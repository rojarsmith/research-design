# 第四課 Timer、中斷與非阻塞流程

這一課約 5 至 8 小時。目標是讓取樣、LED、按鈕與命令接收同時前進，而且能量出每一項晚了多少。讀完應該能解釋：為什麼加了中斷，取樣仍然可能漏掉；為什麼關中斷的時間就是其他中斷延遲的下限。

## 一次中斷經過哪些步驟

以 Cortex-M 為例，周邊事件到 handler 執行之間有好幾個狀態，每一個都可能是問題所在：

```text
周邊事件發生 → 周邊設定自己的狀態旗標
    → 若該周邊的中斷致能已開：送出中斷請求
    → NVIC 把該中斷標成 pending
    → 若 NVIC 已致能這個中斷、優先權足夠：進入例外
    → 硬體把 8 個暫存器推進 stack，從向量表取 handler 地址
    → handler 執行：清周邊旗標、搬最少的資料、通知主迴圈
    → 返回：硬體從 stack 恢復暫存器
```

進入例外時，硬體推入 R0 到 R3、R12、LR、PC 與 xPSR 共八個 word，並把 EXC_RETURN 值寫進 LR。[Cortex-M4 Generic User Guide](https://support.arm.com/documentation/dui0553/latest/) Arm 的 C 呼叫慣例規定被呼叫的函式要保存 r4 到 r8、r10、r11 與 SP，r0 到 r3 和 r12 則可以被覆寫，所以硬體推入的正好是一般 C 函式可能破壞、又沒有義務保存的那一組；handler 因此可以直接寫成 C 函式。[AAPCS32](https://github.com/ARM-software/abi-aa/blob/main/aapcs32/aapcs32.rst) 代價是 ISR 也要用 stack，stack 大小必須把最深的中斷巢狀算進去。

幾條會直接影響程式行為的規則，都來自 Arm 的使用手冊：

- 優先權數值越小越優先；Reset、NMI 與 HardFault 的優先權固定且最高。相同優先權的中斷不會互相搶占。
- 每個優先權欄位是 8 bits，但晶片只實作其中高位的幾個，未實作的低位元讀為 0、忽略寫入。Cortex-M0+ 只實作 bits[7:6]，也就是 4 個等級。[Cortex-M0+ Generic User Guide](https://support.arm.com/documentation/dui0662/latest/)
- 中斷沒有被致能時，請求仍會讓它變成 pending，只是不會進入。先清掉舊的 pending 再致能，否則一致能就會立刻進入一次。
- pending 是一個狀態，不是計數器。同一個中斷在 pending 期間再發生一次，仍然只會進入一次。
- 對於 level-sensitive 的中斷，如果 handler 返回前沒有讓周邊撤除請求，中斷會立刻再次 pending，處理器又進入同一個 handler。主迴圈從此得不到執行時間。

## SysTick：第一個時間來源

SysTick 是 Cortex-M 核心內的 24 位元遞減計數器，數到 0 時重新載入 RELOAD 值，並可產生 SysTick 例外。要每 N 個時脈週期觸發一次，RELOAD 設為 N − 1。時脈來源可以是處理器時脈或晶片提供的外部參考時脈。處理器被 debugger 停住時，計數器不會遞減。[Cortex-M4 Generic User Guide](https://support.arm.com/documentation/dui0553/latest/) 在 Cortex-M0 與 Cortex-M0+ 上 SysTick 是選配，要先確認你的晶片有實作。[Cortex-M0 Generic User Guide](https://support.arm.com/documentation/dui0497/latest/)

例如處理器時脈 48 MHz、要 1 ms tick：N = 48,000，RELOAD = 47,999。24 位元能表示的最長週期是 2^24 個時脈，在 48 MHz 下約 0.35 秒。

tick ISR 通常只做一件事：把一個 32 位元的毫秒計數加 1。以 1 kHz 計數，2^32 ms 約 49.7 天後回繞。比較時間一律用經過時間：

```c
/* 正確：unsigned 減法有模數語意，回繞前後都對 */
if ((uint32_t)(now - last) >= period) { ... }

/* 錯誤：deadline 回繞成小數字時，這個條件會連續成立 */
if (now >= deadline) { ... }
```

C 標準規定 unsigned 運算的結果以模數方式縮減，不會溢位，這正是第一課提到的差異。[C11 N1570](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)

讀這個計數器也要小心。32 位元核心讀一個對齊的 32 位元變數通常一次完成；8 位元或 16 位元 MCU 則要分兩次讀，中斷可能插在兩次之間，讀到「低半是舊的、高半是新的」值。這種撕裂讀取的解法是重讀直到高半穩定，或讀取時短暫關中斷。你的核心對哪些存取保證一次完成，要查 core manual 的記憶體模型章節。

## ISR 的工作規則

- 短：清旗標、搬最少的資料、留下事件，其餘交給主迴圈。
- 不等待：ISR 裡不 busy wait、不呼叫可能阻塞的函式。
- 所有權明確：一個變數只有一方寫入。ISR 設旗標、主迴圈清旗標的寫法，在 ISR 連續觸發兩次時會漏事件；改用 ISR 只增加的計數器，主迴圈記住自己上次看到的值。
- `volatile` 讓編譯器每次都真的去讀，但不提供原子性，也不保證多個變數之間的一致性。
- 關中斷的時間要短且可量測。關中斷期間到達的中斷只能等待；關得比 tick 週期還久，兩次 tick 會合併成一次，時間基準從此落後。

## 非阻塞主迴圈與逾期策略

第一課的迴圈已經把時間和工作分開。這一課要補上兩件事：工作逾期時怎麼辦，以及怎麼量出逾期。

| 策略 | 做法 | 結果 |
| --- | --- | --- |
| 逐期補做 | 期限每次只往前推一個週期 | 筆數補齊，但補做的樣本晚到而且擠在一起 |
| 跳過並計數 | 直接跳到最新一期，跳過的期數加進計數器 | 時間戳維持等間隔，遺失可被觀察 |
| 從現在重新起算 | 下次期限 = 現在 + 週期 | 筆數變少，相位漂移，而且沒有任何紀錄 |

資料採集器選「跳過並計數」：時間戳保持在格點上，錯過的期數透過狀態回報給電腦。前兩種都可以是合理選擇，第三種的問題是遺失不留痕跡。

兩個量測名詞要分清楚：延遲是事件發生到開始處理的時間，抖動是這段時間的變化範圍。主迴圈輪詢的最差延遲，大約是最長的那一項工作加上一輪迴圈的成本。

按鈕去彈跳也是一個小狀態機：原始輸入和目前認定的狀態不同，而且連續維持 10 ms，才承認改變。門檻同時定義了「最短可辨認的按壓」，太短的碰觸會被濾掉；門檻要依按鈕的彈跳時間與想要的反應速度選擇。

## 桌機實驗

[labs/03-timer-scheduler/sched_sim.c](../labs/03-timer-scheduler/sched_sim.c) 用虛擬時間模擬 1 ms tick 中斷、10 ms 取樣、500 ms LED 與隨機到達的命令。所有成本數字都是假設值，用來比較設計，不代表任何晶片。

```sh
cd labs/03-timer-scheduler
gcc -std=c11 -Wall -Wextra -Werror -O2 -o sched_sim sched_sim.c
./sched_sim
./sched_sim --test
```

執行之前，先預測每個情境的樣本數、錯過數與最晚延遲。以下是一次執行的輸出，時間單位是 µs：

```text
case policy         samples missed  max_late avg_late   lost  cmd_wait
A    skip+count  1000/1000       0       144        4      0        49
B    skip+count   962/1000      38       267        9      0     29465
C    catch-up    1000/1000       0     20267      593      0     29462
D    rebase       962/1000       0     20267      404      0     29465
E    isr         1000/1000       0         0        0      0     29402
F    isr         1000/1000       0       260        3      0     29717
G    isr          853/1000       0   1483000   735578   1484     29802
```

讀表時回答：

- A 的最晚延遲為什麼接近 150 µs？找出模擬裡最長的那一項工作。
- B、C、D 都被同一個 30 ms busy wait 拖累，差別在哪一欄？哪一個讓遺失消失得無聲無息？
- E 把取樣移進 tick ISR，取樣不再受 busy wait 影響，但命令等待時間為什麼沒有改善？
- F 和 G 只差在關中斷的長度。G 的 lost 欄代表什麼？為什麼 G 的取樣時間落後了將近 1.5 秒？

`--test` 另外檢查三件事：計數器從 0xFFFFFFCE 開始跑 100 ms 時，錯誤的比較法執行了 13 次而不是 10 次；16 位元匯流排在 0x0000FFFF 變成 0x00010000 的瞬間讀到 0x0001FFFF；去彈跳後 20 次按壓恰好產生 20 個按下與 20 個放開事件。

## 上板實作

1. 依處理器時脈算出 1 ms tick 的 RELOAD，設定 SysTick 或晶片的 timer。在 ISR 裡切換一支 GPIO，用邏輯分析儀量週期；沒有儀器時，讓 LED 每秒切換並用 60 秒碼錶比對。
2. 寫出非阻塞主迴圈：每 10 ms 產生一筆模擬資料並計數、每 500 ms 切換 LED、按鈕去彈跳、輪詢 UART 是否收到位元組（下一課才解析）。
3. 量抖動：在取樣工作開頭切換另一支 GPIO，用邏輯分析儀量週期的最小與最大值。沒有儀器時，在取樣開頭讀一個高解析度計數器並累計最小、最大間隔。Cortex-M3、M4、M7 常有 DWT 週期計數器，但它是可選的除錯元件；Cortex-M0、M0+ 沒有這個計數器，改用硬體 timer。[Keil ULINKplus 說明](https://www.keil.com/support/docs/3999.htm)
4. 在 LED 工作裡加入 30 ms 的 busy wait，記錄錯過的取樣數、按鈕反應與 UART 輪詢的延遲，然後移除它。
5. 用一個廠商 timer 中斷做故障注入：故意不清它的狀態旗標，觀察主迴圈是否停擺、debugger 停下時 PC 是否總在同一個 handler。SysTick 的 pending 在進入例外時就會自動清除，所以這個實驗要用一般周邊的 timer。
6. 在 debugger 停住 10 秒再繼續，比較 tick 計數和實際經過的時間。SysTick 停止計數；其他周邊 timer 在除錯暫停時是否繼續跑，依晶片的除錯設定而定，要查 reference manual。

| 驗收條件 | 要留下的證據 |
| --- | --- |
| 取樣排程與命令接收可同時前進 | 取樣計數與命令處理在同一段時間內都持續增加 |
| 量測週期和抖動 | 量測方法、樣本數、週期的最小、平均、最大值 |
| 說明 busy wait 的影響 | 加入前後的錯過數、最晚延遲、按鈕或命令的延遲 |

## 先自行回答

1. 處理器時脈 72 MHz，要 1 ms 的 SysTick，RELOAD 是多少？這個時脈下 SysTick 最長能設多長的週期？
2. tick 是 32 位元毫秒計數。`if (now >= last + 10)` 什麼時候會出錯？
3. tick 為 1 ms，某段程式關中斷 2.5 ms。tick 計數會怎樣？
4. ISR 設 `g_sample_ready = 1`，主迴圈處理後清成 0。主迴圈卡住期間 ISR 觸發了兩次，會發生什麼？
5. 主迴圈裡最長的工作是 3 ms 的命令處理，其次是 1 ms 的傳送。輪詢式取樣的最大延遲大約多少？

### 解析

1. RELOAD = 72,000 − 1 = 71,999。最長週期是 2^24 ÷ 72 MHz ≈ 0.233 秒。
2. `last + 10` 在接近 2^32 時回繞成很小的數字，`now` 仍然很大，條件立刻成立並連續觸發，約在開機 49.7 天時出現。改成 `(uint32_t)(now - last) >= 10`。
3. 關中斷期間有兩到三次 tick 到期，但 pending 只記得「有」，開中斷後只進入一次 ISR，計數少了一到兩次，時間基準永久落後。
4. 第二次事件被第一次的旗標吸收，主迴圈只看到一次。用 ISR 只增加的計數器，或把事件放進第五課的環形緩衝區。
5. 約 3 ms 加上一輪迴圈的成本，前提是每一項工作都有上限。若要求更小的抖動，把取樣交給 timer 中斷或讓硬體自行觸發取樣，並重新檢查 ISR 的工作量。
