# 第八課 Watchdog、重啟與設定保存

這一課約 5 至 8 小時。資料採集器已經能取樣、傳送、接受命令；這一課讓它出錯之後自己回到已知狀態，並把設定安全地留到下一次開機。讀完應該能解釋：為什麼在 timer 中斷裡餵狗等於沒有 watchdog；為什麼設定要存兩份，而且寫的永遠是沒有生效的那一份。

## 這一課要回答的四個問題

| 問題 | 機制 | 證據去哪裡找 |
| --- | --- | --- |
| 程式卡住時誰把它拉回來 | watchdog 與報到式監督 | watchdog 的時脈與逾時、每個活動的報到位置 |
| 開機時怎麼知道上一次是怎麼結束的 | 重啟原因旗標、不清零的開機紀錄 | reference manual 的 reset 章節、.noinit 區 |
| 一直重啟時怎麼停下來 | 連續當機計數與安全模式 | 每次開機的原因與計數 |
| 設定怎麼撐過斷電 | Flash 的抹除規則、雙槽、序號與 CRC | 每一個寫入步驟斷電後的開機結果 |

## 三種不正常

- 卡死：主迴圈停在沒有上限的等待裡，例如 `while (!sensor_ready()) {}`。中斷照跑，主迴圈不再前進。
- 停滯：主迴圈照跑，某一項活動卻沒有進度。例如 TX 中斷被關掉後沒有再打開，取樣照常放進緩衝區，一個 byte 都送不出去。
- 當機循環：每次開機都很快又出事，例如一份通過範圍檢查、卻觸發 bug 的設定。

恢復的手段由輕到重：重試、重設那個周邊、讓 watchdog 重啟整個系統、以安全模式開機。小範圍的恢復程式本身也可能卡住，所以最後一道防線必須是不依賴軟體正確性的硬體 watchdog。

## 兩種 watchdog

watchdog 是一個獨立計數的 timer。軟體必須在逾時前用規定的方式讓它重新計數，俗稱餵狗，否則它重啟系統。

| | 獨立 watchdog | window watchdog |
| --- | --- | --- |
| 什麼時候重啟 | 太久沒餵 | 太久沒餵，或在 window 打開之前就餵 |
| 時脈 | 通常有自己的低速振盪器，主時脈壞了照樣計時 | 依晶片而定，有些接在周邊匯流排時脈上 |
| 抓得到 | 卡死；配合報到式監督也抓得到停滯 | 同左，再加上跑得太快：時間基準錯了、流程跳過了該做的工作 |
| 常見限制 | 啟動後常無法用軟體關閉；逾時精度不高 | 餵狗時間必須落在 window 之內，要先量清楚主迴圈的時間 |

能不能關閉、debugger 暫停時是否一起停、休眠時是否繼續計數，各家不同，要查 reference manual 的 watchdog 章節。沒設好暫停時的行為，一停在斷點上就被重啟。window watchdog 只有在它的時脈和系統時脈不同源時，才抓得到系統時脈設錯：同源時兩者一起變快。

## 報到式監督

watchdog 只能確認有人在餵，不能確認系統在做該做的事。餵狗的條件決定了它抓得到什麼：

| 餵狗的位置 | 主迴圈卡死 | 單一活動停滯 |
| --- | --- | --- |
| timer 中斷裡，無條件 | 抓不到：中斷照跑，照樣餵 | 抓不到 |
| 主迴圈每一圈，無條件 | 抓得到 | 抓不到：主迴圈照跑，照樣餵 |
| 主迴圈裡，所有活動都報到過才餵 | 抓得到 | 抓得到，而且知道是哪一個 |

規則：

1. 每個受監督的活動有自己的期限。實驗裡取樣是週期的三倍加 50 ms，上傳 200 ms，命令處理 100 ms。
2. 活動在證明自己有進度的位置報到。沒收到命令時，命令活動只要確實檢查過接收緩衝區就算報到；上傳活動有資料卻一個 byte 都沒送出，即使函式每圈都被呼叫，也不能報到。
3. 主迴圈裡只有一個餵狗點：所有活動都在期限內，而且距上次餵狗已過固定間隔，才餵。間隔固定，才能配合 window watchdog。
4. 一旦有活動逾期就不再餵，並在停止之前把是哪個活動寫進不清零的 RAM。
5. ISR 不直接報到，只增加計數，由主迴圈檢查計數有沒有前進；第六課的 DMA 完成次數也一樣。如果你在第七課加了 RTOS，各 task 報到，由一個監督 task 決定是否餵狗，不要讓每個 task 都能餵。

逾時要大於正常情況下最長的不餵狗時間，例如寫 Flash 時 CPU 停住的時間，也要小於系統能容忍的恢復時間。在長時間工作中間插入餵狗，例如在抹除 Flash 的迴圈裡餵，是另一種無條件餵狗。

斷線不是重啟的理由。第五課提到電腦定期送命令當作心跳；這一課的設定加入 `link_timeout_ms`，超時就標示斷線、改變輸出行為。命令活動的報到若依賴有沒有收到命令，電腦一關，裝置就反覆重啟。

## 開機時先讀重啟原因

多數晶片有記錄重啟原因的旗標，例如上電、reset 接腳、watchdog、軟體要求、低電壓。很多晶片的旗標會累積到軟體清除為止，上電時通常只剩上電旗標；確切行為要查 reference manual 的 reset 章節。開機時依序：

1. 盡早讀出並保存旗標，接著清除。不清除，下一次就分不清旗標是哪一次留下的。
2. 依手冊的規則解讀。例如有些晶片在內部重啟時，reset 接腳的旗標也會成立。
3. 讀第二課 .noinit 區裡的開機紀錄，用 magic 與檢查碼確認可信；上電後一律當作不可信。
4. 更新紀錄：watchdog 造成的重啟讓連續當機計數加 1；讀出上一次留下的停滯活動後清掉。

韌體要主動重啟時，Cortex-M 可以寫 AIRCR 的 SYSRESETREQ 位元，同一次寫入的 VECTKEY 欄位必須是 0x5FA，否則寫入被忽略；實際重設哪些部分由晶片決定。[Cortex-M4 Generic User Guide](https://support.arm.com/documentation/dui0553/latest/) 主動重啟前同樣先把原因寫進紀錄。

## 當機循環與安全模式

連續當機計數：watchdog 重啟加 1；穩定運作一段時間後歸零；reset 鍵與軟體主動重啟不加也不清。達到門檻就進入安全模式，實驗用 3：用預設設定開機，但不抹除存著的那份，留給電腦檢查；只保留命令、狀態回報與基本取樣；在狀態回報中標示安全模式；收到並存好新設定之後才清除計數。

穩定的門檻不能太早：一開機就清除計數，當機循環永遠偵測不到。也不能完全不清：相隔幾天的偶發卡死累積起來，會被誤判成當機循環。

## 把設定存進 Flash

多數內建 NOR Flash 的規則如下，細節查 reference manual 的 Flash 章節與 datasheet：

- 抹除以頁或 sector 為單位，抹除後每個 bit 都是 1。寫入只能把 1 變成 0，要變回 1 只能抹除整頁。有些晶片的寫入單位是 8 bytes 並帶 ECC，同一處在抹除前只能寫一次。
- 抹寫次數有限。抹除一頁可能要數毫秒到數十毫秒，很多晶片在這段期間從同一塊 Flash 讀指令會讓 CPU 停住，中斷也跟著延遲。
- 設定頁要在 linker script 裡從程式區排除，否則下一版韌體變大時會蓋到它。

雙槽：每個槽一頁，內容是 `magic | 版本 | 長度 | 序號 | 設定內容 | CRC-32`，欄位逐 byte 組裝。寫入時永遠寫沒有生效的那一槽，順序是抹除、寫入 CRC 以外的內容、最後寫 CRC，寫完讀回比對。載入時兩槽都檢查 magic、長度、CRC、版本與數值範圍；都有效取序號較新的，只有一個有效就用它，都無效就用預設值，並回報每一槽的判定。

| 斷電發生在 | 正在寫的那一槽 | 開機結果 |
| --- | --- | --- |
| 抹除、寫入內容或寫入 CRC 的途中 | 內容不完整，CRC 不符 | 另一槽的上一份好設定 |
| 寫完之後 | 新設定有效，序號較新 | 新的一份 |

只有一個槽時，抹除開始的那一刻就失去了唯一的一份。CRC 防的不只是斷電：數值仍在合理範圍內的位元錯誤，只有 CRC 抓得到。斷電時正在寫的位置，在真實晶片上可能處於不穩定狀態，每次讀回不同；所以寫入成功要定義成讀回一致。

序號用模數差比較：`(uint32_t)(a - b)` 落在 1 到 2^31 − 1 才算 a 比較新。直接比大小，序號從 0xFFFFFFFF 回繞到 0 時會選到舊的那一份。

無效的記錄整份拒絕，不逐欄修補；命令收到的無效值在寫入前就以 NACK 拒絕，永遠不把無效設定寫進 Flash。記錄帶版本：讀到舊版就轉換成新格式、新欄位填預設值，驗證後寫到另一槽，舊的那份留作備份；讀到不認得的版本就不要猜，退回另一槽或預設值。也不要每收到一個命令就寫 Flash，收到明確的儲存命令，或設定維持一段時間不變之後再寫。

## 休眠與 watchdog、tick

Cortex-M 的 WFI 讓處理器停止執行並進入休眠，通常等到足夠優先權的例外才醒來；WFE 依事件暫存器決定是否進入休眠；SCR 的 SLEEPONEXIT 讓處理器處理完例外後直接回到休眠。實作哪幾種休眠模式由晶片決定；有兩種時，SCR 的 SLEEPDEEP 選較深的那一種，使用手冊描述的深度休眠會停掉系統時脈、關掉 PLL 與 Flash。debugger 的操作也可能把處理器叫醒，休眠程式要能醒來後再回去睡。[Cortex-M4 Generic User Guide](https://support.arm.com/documentation/dui0553/latest/)

淺休眠通常只停處理器時脈，tick 與周邊照跑，任何中斷都能叫醒。深度休眠時 tick 可能停止，只有特定來源能叫醒，例如外部接腳、RTC 鬧鐘、低功耗 UART；哪些來源能用在哪種休眠，查 reference manual 的低功耗章節。

- watchdog：很多晶片的獨立 watchdog 在休眠時照樣計數。睡得比逾時久，就在休眠中被重啟，重啟後又回去睡。解法是設定比逾時短的週期喚醒，醒來讓活動報到再餵；或在晶片支援時讓 watchdog 在休眠中暫停，代價是休眠中卡住沒有人管。
- tick：醒來後毫秒計數落後，取樣期限與各種逾時跟著錯。醒來時用持續運作的時間來源，例如 RTC，補上睡掉的時間。

量測功耗需要合適的電流量測方法，這一課不要求。

## 桌機實驗

[labs/07-watchdog-recovery](../labs/07-watchdog-recovery/) 用虛擬時間模擬 watchdog、重啟原因暫存器、不清零的 RAM、可以在任何一步斷電的 Flash，以及簡化的資料採集器。[supervisor.c](../labs/07-watchdog-recovery/supervisor.c)、[boot_guard.c](../labs/07-watchdog-recovery/boot_guard.c)、[config_store.c](../labs/07-watchdog-recovery/config_store.c) 不碰暫存器，可以原封不動搬上板；config_store.c 只透過三個 Flash 函式存取硬體。[recovery_sim.c](../labs/07-watchdog-recovery/recovery_sim.c) 是硬體模型、韌體骨架與自我檢查。

```sh
cd labs/07-watchdog-recovery
gcc -std=c11 -Wall -Wextra -Werror -O2 -o recovery_sim recovery_sim.c supervisor.c boot_guard.c config_store.c
./recovery_sim
./recovery_sim --test
```

數字都是教學用的假設：獨立 watchdog 逾時 500 ms、每 100 ms 考慮餵一次、穩定 3 秒才清除當機計數。以下是預設執行的部分輸出：

```text
主迴圈卡死（等待感測器沒有上限）：注入於 2001 ms，重啟於 2499 ms（498 ms 後），原因 watchdog，回報停住的活動：沒有紀錄（主迴圈停住，supervisor 也停了）
上傳停滯（TX 中斷被關掉，主迴圈照跑）：注入於 2001 ms，重啟於 2699 ms（698 ms 後），原因 watchdog，回報停住的活動：上傳
  一次寫入共 7 個動作：抹除 1 次、寫入 6 個 word，CRC 最後寫
  兩個槽：已有設定 X，寫入 Y
    1:舊 2:舊 3:舊 4:舊 5:舊 6:舊 7:舊 不斷電:新
```

讀輸出時回答：上傳停滯晚了約 200 ms 才重啟，多出來的是什麼？主迴圈卡死後，為什麼不知道是誰停住？當機循環為什麼第 4 次開機才進安全模式，那份會出事的設定還在嗎？window watchdog 在 tick 快一倍時重啟，獨立 watchdog 為什麼看不出來？深度休眠時 RTC 每 600 ms 喚醒為什麼不夠？

接著用錯誤的設計重跑。先寫預測，再執行 `./recovery_sim --fault=名稱` 對照：

| 錯誤設計 | 你的預測 | 實際觀察 |
| --- | --- | --- |
| isr-feed：在 tick 中斷裡無條件餵狗 | | |
| loop-feed：主迴圈每圈無條件餵狗 | | |
| keep-reset-flags：讀了重啟原因卻不清除 | | |
| early-stable：一開機就宣告穩定 | | |
| single-slot：設定只存一個槽 | | |

注意 keep-reset-flags：上電旗標一直留著，之後每次 watchdog 重啟都被當成上電，開機紀錄每次重設，當機循環永遠偵測不到。也注意前兩種設計下的 window watchdog：無條件餵狗本身就違反 window，時脈正確也一直重啟。

`--test` 檢查報到式監督、兩種卡死的偵測與恢復、兩種錯誤餵法各漏掉什麼、四種重啟原因的判讀、當機循環與安全模式、一次寫入的每一個動作斷電、單槽的遺失、無效數值與位元翻轉與未知版本、序號回繞、v1 升級、抹寫平均，以及 window watchdog 與休眠。全部通過之後，試著改壞一處。以下每一項都在 Windows 11、GCC 16.2 上實際改過，並確認右欄的檢查失敗：

| 改壞一處 | 失敗的檢查 |
| --- | --- |
| recovery_sim.c：上傳活動不論有沒有送出資料都報到 | 只有上傳停住也被偵測 |
| config_store.c：`config_save` 的目標改成 `st->active == 1 ? 1u : 0u`，也就是覆寫生效中的那一槽 | 輪流寫入、斷電掃描、升級、抹寫平均 |
| config_store.c：拿掉載入時的 CRC 比對 | 位元翻轉、第一次寫入就斷電 |
| config_store.c：`seq_newer` 改成 `return a > b;` | 序號回繞 |
| config_store.c：`config_save` 不先抹除就寫入 | 輪流寫入的第三次、斷電掃描的不斷電那一次、抹寫平均 |
| boot_guard.c：`boot_guard_start` 改完欄位後沒有呼叫 `seal()` | 當機循環、安全模式 |

拿掉 CRC 比對之後，已有舊設定時的斷電掃描仍然通過，因為寫到一半的記錄通常連長度或數值範圍都通不過；讓它露餡的是內容看起來完全合理的錯誤。這個模型不能證明真實 Flash 斷電後的位元狀態、抹除時間與耐用度、watchdog 的實際逾時誤差、reset 對周邊的影響與休眠電流。

## 上板實作

1. 讀 reference manual 並記下章節與版本：watchdog 的時脈、逾時公式、能否關閉、除錯暫停與休眠時的行為；重啟原因旗標的位置、清除方式與解讀規則；Flash 的頁大小、寫入單位、抹除時間、抹寫次數；低功耗模式與喚醒來源。
2. 在 linker script 保留兩頁給設定、一塊 .noinit 給開機紀錄，用 map file 確認程式沒有蓋到它們。
3. 用晶片的 Flash driver 實作 config_store.c 要的三個函式，等待一律要有上限。用一支 GPIO 包住抹除，以邏輯分析儀量出抹除時間，和 watchdog 逾時比較。
4. 開機流程：讀並清除重啟原因、boot_guard、載入設定、啟動 watchdog。開機結果先用 debugger 讀；要讓電腦看到，就新增一個封包類型，並同時更新 host_rx.c 與 rx_check.c 的測試。
5. 接上報到式監督：取樣活動看第五課 logger 的序號有沒有前進，因為每個取樣期限都會產生一個封包，不論成功、逾時或被丟棄；上傳活動看 TX 緩衝區是否為空，或 tail 有沒有前進；命令活動每次檢查過接收緩衝區就報到。
6. 故障注入，每一項都要能恢復：用除錯命令讓主迴圈進入無窮迴圈；執行中用 debugger 清掉 UART 的 TX 中斷致能位元；暫時改成在 tick 中斷裡餵狗做對照，然後改回來；停在斷點超過逾時，比較開與不開除錯暫停設定；送一份會讓某活動卡死的設定；讓韌體每 200 ms 交替寫入兩份設定，在任意時刻切斷電源 20 次，用可控開關的電源或 USB 集線器會比反覆拔插接頭好；用燒錄工具抹除設定頁，再用除錯命令寫入 CRC 錯、數值超出範圍、版本不認得的記錄。

| 驗收條件 | 操作 | 要留下的證據 |
| --- | --- | --- |
| 注入卡死後可恢復 | 主迴圈卡死與上傳停滯各 5 次 | 每次都重啟、原因判讀為 watchdog、停滯的活動被記下；注入到重啟的時間；電腦端資料流恢復 |
| 無效設定有預設值 | 抹除設定頁；寫入 CRC 錯、超出範圍、版本不認得的記錄 | 每次都以上一份好設定或預設值開機，並回報每一槽的判定 |
| 不以無條件餵狗掩蓋故障 | 程式碼審查；在 tick 中斷裡餵狗的對照實驗 | 只有一個餵狗點，條件是所有活動都報到；對照實驗中卡死沒有被偵測的紀錄 |
| 寫入時斷電不遺失設定 | 寫入期間斷電 20 次 | 每次開機都是舊值或新值，沒有一次是預設值或錯誤值 |
| 當機循環會停下來 | 寫入一份會觸發卡死的設定 | 第幾次開機進入安全模式；修正設定後回到一般模式 |

斷電 20 次只能證明這 20 次沒出錯；桌機實驗的逐步掃描補的是其餘的時間點，兩者要一起看。

## 先自行回答

1. watchdog 逾時 500 ms，每 100 ms 考慮餵一次，上傳活動的期限是 200 ms。上傳停住後，最慢多久會重啟？
2. 抹除一頁 Flash 最長 40 ms，期間 CPU 停住；watchdog 逾時 30 ms。該怎麼辦？
3. 開機時讀到的旗標同時有 watchdog 與 reset 接腳，可能是什麼情況？
4. 槽 A 序號 41、CRC 正確但 period 是 0；槽 B 序號 40、有效。開機用哪一份？下一次寫到哪一槽、序號多少？
5. 裝置每 10 秒深度休眠一次，獨立 watchdog 逾時 1 秒，休眠時照樣計數。有哪些做法？代價各是什麼？

### 解析

1. 停住 200 ms 後才被判定；最後一次成功的餵狗可能就在判定前一刻，再等 500 ms，所以約 700 ms，加上一圈主迴圈的時間。實驗裡是 698 ms。
2. CPU 停住時沒有程式能餵狗，在抹除前後多餵一次也沒用。把逾時設得大於抹除時間加餵狗間隔再加餘裕；需求不允許時，查晶片是否有雙 bank 或從 RAM 執行抹除的方式，讓 CPU 不必停住。抹除期間中斷也會延遲，要一併檢查 UART 的接收期限。
3. 上一次開機沒有清除旗標，兩次重啟的旗標疊在一起；或晶片在內部重啟時也讓接腳旗標成立。查手冊的解讀規則，並確認開機程式有清除。
4. 用槽 B，槽 A 因數值無效被拒絕。下一次寫到沒有生效的槽 A，序號是 41，也就是生效那一份加 1；寫完後槽 A 是有效而且較新的一份。
5. 用 RTC 每不到 1 秒喚醒，讓活動報到再餵，代價是功耗略增；在晶片支援時讓 watchdog 在休眠中暫停，代價是休眠中卡住沒有人管；加長逾時，代價是醒著時卡死要更久才恢復。不論哪一種，醒來都要用 RTC 補上 tick。
