# 04 使用情境與研究路線

[回主報告](../README.zh-TW.md) · 查核日期：2026-10-21

本篇是依前述來源提出的工程判斷框架，不是已完成產品評測，也不針對特定公司。

## 哪些需求值得優先驗證

| 情境 | 可能價值 | 第一個反證實驗 |
| --- | --- | --- |
| 重用成熟 C/C++ 演算法庫 | 減少重寫與維護兩份實作的成本 | 選一個 API，確認所有相依庫與系統呼叫能移植 |
| 影像處理、壓縮、數值運算 | 將成塊運算集中在編譯程式內 | 在目標低階裝置比較端到端時間與記憶體 |
| 既有遊戲或桌面核心上 Web | 重用核心程式碼與資料格式 | 先驗證輸入、圖形、檔案、執行緒與事件迴圈 |
| 一般表單、列表與互動 UI | 多數工作不是計算瓶頸 | 先量測 DOM、網路與框架成本，確認是否有 Wasm 可處理的熱點 |
| 瀏覽器外外掛或元件 | 明確介面與隔離的可攜執行單位 | 驗證 runtime 的 world、介面版本、資源限制與取消能力 |

參考依據：[C 函式庫移植](https://web.dev/articles/emscripting-a-c-library)、[效能模式](https://web.dev/articles/webassembly-performance-patterns-for-web-apps)、[Component Model](https://component-model.bytecodealliance.org/introduction.html)。這些依據支持可行方向，沒有提供本表各情境的通用效能倍數。

## 選工具先選宿主

- **既有 C/C++ 要進瀏覽器**：先試 Emscripten，重點在相依庫與 Web 整合。
- **全新 Web 功能**：先建立 JavaScript/TypeScript 基線，再決定是否值得導入額外語言與工具鏈。
- **Rust 或其他語言要進瀏覽器**：確認該語言的 Web 綁定、目標與資料傳遞工具；不能直接套用 C/C++ 的建置選項。本研究尚未逐一驗證各語言工具版本。
- **瀏覽器外元件**：從所需 WASI world、runtime 與元件工具相容性反推工具鏈；不要預期 Emscripten 的 Web loader 可直接搬過去。

以上是選型推論；基礎概念見 [MDN](https://developer.mozilla.org/en-US/docs/WebAssembly/Guides/Concepts)，宿主介面現況見 [WASI 0.3](https://wasi.dev/releases/wasi-p3)。

## 四個階段的實驗

| 階段 | 交付 | 通過條件 |
| --- | --- | --- |
| 1. 建立可重現鏈路 | 02 的小型 C 函式、版本紀錄與建置 log | 由乾淨目錄重建，瀏覽器結果正確 |
| 2. 接近真實需求 | 一個實際 API，含代表性和錯誤輸入 | 輸出與現有基線一致，配置和釋放契約明確 |
| 3. 比較價值 | JS/Worker/Wasm 的對照量測 | 達到事先定義的延遲、體積及記憶體預算 |
| 4. 驗證交付 | 測試站點、快取策略、降級與回滾紀錄 | 實際瀏覽器與裝置矩陣通過，能重現失敗與恢復 |

每個階段都可停在證據不足處；「成功編出 Wasm」只完成第一階段的一部分。
