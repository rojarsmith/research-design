# api-gateway 複盤要點

做完再讀。這裡記的是洞見，不是程式碼。

## 第 1 階段

- **根因**：`normalize_path` 先把整個 target 做 percent-decode，才切掉查詢字串、再用 `/` 切段。結果 `%2F` 變成真的斜線，多切出一段；`%3F` 變成 `?`，後面的路徑被當成查詢字串丟掉；連查詢字串裡的 `100%` 也被拿去解碼，整個請求被判成無效。
- **怎麼從症狀推出來**：三個看起來無關的症狀（多出來的路徑、被截短的路徑、無效的搜尋請求），共同點是 target 裡都有 `%`。先找出錯誤結果的共同點，再看處理的順序。
- **修法**：先切掉 `?` 和 `#`，再用原始的 `/` 切段，最後每一段各自解碼。README 第 1 到 4 步的順序就是規格。
- **要講得出來**：`collapse_slashes` 每次都從頭 `find("//")`，再 `erase` 一個字元，連續的斜線很多時是 O(L²)。正常的路徑很短，所以看不出來，這是第 3 階段的伏筆。而且切段時本來就會丟掉空的段，這個迴圈其實是多餘的。

## 第 2 階段

- **規則的重點**：先比路徑樣式的具體程度，再比方法；只有樣式完全相同時，精確的方法才勝過 `ANY`。405 的意思是「有路由符合路徑，但沒有一條允許這個方法」。
- **資料結構**：以「段」為節點的 trie。每個節點有字面段的雜湊表、一個參數子節點、一個萬用字元子節點，以及在這裡結束的路由。參數名稱不同的路由共用同一個參數子節點，名稱存在路由上。
- **為什麼 DFS 的順序就是答案**：在每個節點依「字面 → 參數 → 萬用字元」的順序往下找，完整的匹配就會依具體程度由高到低出現。第一個允許這個方法的就是答案，不需要先收集全部再排序。找不到時再走一次，收集所有符合路徑的路由的方法，回 405。
- **重複的路由**：同一個方法落在 trie 的同一個節點上就是重複，建表時就能檢查，不需要兩兩比較。
- **容易錯的地方**：
  - 萬用字元至少要吃一段，`/files` 不符合 `/files/*path`。
  - 第一個不同的位置決定勝負：`/a/b/*rest` 勝過 `/a/:x/c`。
  - 方法區分大小寫，`get` 不是 `GET`。
  - 參數值是解碼後的段，`a%2Fb` 的值是 `a/b`。
- **複雜度**：每個請求是 O(L) 的正規化，加上 trie 裡沿著路徑走過的節點數，跟路由的總數無關。

## 第 3 階段

三個測資各自打掉不同的寫法。下表是在 Windows 11、g++ 16.2.0 上的實測，時間上限 1.5 秒：

| 寫法 | large-1 400 個服務 | large-2 同一個前綴 | large-3 掃描器流量 |
| --- | --- | --- | --- |
| 每個請求檢查全部路由 | 逾時 | 逾時 | 1.15 秒 |
| 依第一段分桶，桶內逐條檢查 | 0.94 秒 | 逾時 | 0.26 秒 |
| trie，但 405 靠逐條檢查全部路由 | 逾時 | 逾時 | 0.76 秒 |
| trie，沿用原本的 `collapse_slashes` | 0.32 秒 | 0.35 秒 | 逾時 |
| 參考解（trie，路徑只掃一次） | 0.23 秒 | 0.27 秒 | 0.19 秒 |

- large-2 打掉「分桶」：所有路由都在 `/api/v3/tenants/:tenant/` 底下，第一段全部一樣。分桶只是把線性掃描的範圍縮小，複雜度沒有變。
- 405 的請求在 large-1 和 large-2 都將近一半。只優化 200 的路徑、405 還是逐條檢查，一樣會逾時。
- large-3 是這個情境的重點：慢的是**原本就有的** `normalize_path`。掃描器送來 12 到 20 KB、充滿連續斜線的 target，`collapse_slashes` 變成 O(L²)。只量 `route_request` 整體看不出來，要把正規化和比對分開計時。
- 「每個請求檢查全部路由」在 large-3 只用 1.15 秒，是因為那裡只有兩千條路由。通過不代表複雜度是對的。
- 討論題的方向：
  - 不中斷地換表：先建好新的表，再用一個原子指標切換，舊的表等進行中的請求都結束再釋放。
  - 依主機名稱或標頭路由：先依主機分成幾張表，再進路徑的 trie；標頭條件放在路由上，在 trie 找到候選之後再檢查。
  - 新路由搶走流量：拿正式流量的紀錄重播，比較新舊兩張表的結果有哪些不同。
