# parking-garage 複盤要點

做完再讀。這裡記的是設計上的取捨，不是標準答案；能通過測試的設計不只一種。

## 核心：把「會變的」和「不會變的」分開

需求階段最該問的一句是「什麼最可能改？」。題目的答案是「價格，和分配車位的方式」，這兩件事就是兩個擴充點。

- **實體**：車位（大小、樓層、編號、是否空著）、停車票（車牌、車種、車位、進場時間）、車種（適合哪些大小、每小時價格）。
- **車種是資料，不是類別階層。** `Motorcycle : Vehicle`、`Car : Vehicle` 這種繼承在這題沒有任何行為差異，只有「適合的大小」和「價格」兩個欄位不同。一張表就夠，新增車種是加一行。
- **分配規則**：誰適合、哪些空著，由停車場算出候選車位；「從候選裡挑哪一個」交給分配策略。策略只排序，不知道車種規則。
- **計費**：一筆停車紀錄（車種、進出時間）交給計費策略算錢。「15 分鐘免費」是每種方案都有的規則，放在共用的函式裡，不要每種方案各寫一次。

## 適合的設計模式

| 模式 | 用在哪裡 | 什麼時候不值得 |
| --- | --- | --- |
| Strategy | 計費方案、分配規則 | 面試官明確說「價格固定、不會變」時，一個函式就夠 |
| Factory（簡單的） | 由名稱 `"capped"`、`"spread"` 建出對應的策略 | 只有一兩種時直接 `if` 也可以，但要放在一個地方 |
| Decorator（可選） | 充電費疊加在任何計費方案上 | 這題用「方案費 + 充電費」兩個函式相加就很清楚 |

Singleton 不適合：停車場本身用 Singleton 會讓測試沒辦法同時建兩座停車場。

## 每個變體在考什麼

| 變體 | 考點 | 好的設計改哪裡 |
| --- | --- | --- |
| 1 計費方案 | 開放封閉原則：新增方案不改舊程式 | 新增兩個計費類別和一個依名稱建立的函式；停車場只多一個 `setPricing` |
| 2 分配規則 | 同上，換成分配 | 新增一個分配類別；候選車位的計算不變 |
| 3 電動車充電 | 跨越多個職責的變動：車種、車位、分配、計費都受影響 | 車種表多兩行和一個欄位、車位多一個欄位、候選車位分兩組、收費多加一項；兩個策略完全不動 |

## 參考設計的改動數字

用 `ood` 量的，只算 src/。兩套參考設計都通過全部 22 個測試；格式是「既有類別 / 既有函式 / 改在既有類別和函式裡的程式碼行」。

| 變體 | Strategy 加車種表的設計 | 車種用字串判斷、樓層各管各的設計 |
| --- | --- | --- |
| 1 計費方案 | 1 / 0 / +1 −0 | 1 / 1 / +12 −0 |
| 2 分配規則 | 1 / 0 / +1 −0 | 1 / 1 / +13 −6 |
| 3 電動車充電 | 4 / 3 / +11 −4 | 3 / 5 / +39 −26 |

- 變體 1 和 2，好的設計完全不改既有的函式，只在 `Garage` 宣告一個新方法。
- 變體 3 是刻意的「跨職責」變動，好的設計也要改四個既有型別。但多數是加一個欄位，邏輯只改三行；散開的寫法要重寫 `enter`、`exit` 和樓層的三個方法。
- 只看「既有類別」的數字，變體 3 好的設計反而比較多（4 對 3）：在結構體加一個欄位也算改了一個類別。所以要一起看既有函式和既有程式碼行，一個數字不夠。

## 各職級的強弱設計（研究報告第 5.3 節）

| 職級 | 弱 | 強 |
| --- | --- | --- |
| 初階 | `Vehicle` 繼承階層，但每個子類別都是空的；車位分配的順序寫錯 | 規則全部做對：最小的合適尺寸、最低樓層、最小編號；費用算對整點 |
| 中階 | 價格和車種用 `if/else` 散在進場、出場兩處；被問「換計費方式」時說要改 `exit` | 計費和分配各自是一個介面，能示範新增一種方案只加一個類別 |
| 高級 | 一開始就做了可設定的規則引擎、預約、多座停車場，35 分鐘寫不完核心 | 先問「什麼會變」，只在那兩處留擴充點；被問到電動車時，說得出它會碰到哪四個地方、為什麼兩個策略不用改 |

## 面試時可以主動講的

- 「車種之間沒有行為差異，我用一張表，不用繼承。」
- 「停車場算出合適的空車位，分配策略只負責挑一個，所以換策略不必知道車種規則。」
- 「15 分鐘免費是所有方案共用的規則，不放在某一個方案裡。」
