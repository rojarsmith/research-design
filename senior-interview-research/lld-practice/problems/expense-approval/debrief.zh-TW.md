# expense-approval 複盤要點

做完再讀。這裡記的是設計上的取捨，不是標準答案；能通過測試的設計不只一種。

## 核心：狀態機要放在哪裡

- **實體**：人（角色、主管）、報銷單（金額、狀態、歷史）。會變動的狀態只有報銷單的狀態和歷史。
- **關鍵的一步**：把「哪個動作、從哪個狀態、到哪個狀態、誰可以做」寫成一張表（轉移表），由一個協調者照表執行：
  找到單 → 找到人 → 查表（`invalid-transition`）→ 檢查權限（`not-allowed`）→ 移動狀態、寫歷史。
  五個動作方法都只是呼叫這一條路。
- **錯誤的先後順序**是題目刻意規定的：先看狀態、再看權限。轉移表讓這個順序只寫一次。
- **歷史由報銷單自己寫**（`moveTo` 同時改狀態和加一行），這是 Tell, Don't Ask：別的類別不需要知道歷史的格式。

常見的另一種寫法是每個動作一個方法，方法裡各自 `if (狀態 == ...)`、各自檢查權限、各自組歷史字串。核心一樣能過測試，但同一條規則會散在五個方法裡。

## 適合的設計模式

| 模式 | 用在哪裡 | 什麼時候不值得 |
| --- | --- | --- |
| 狀態轉移表（或 State 模式） | 動作 × 狀態 → 下一個狀態與權限 | 只有兩三個狀態、規則不會變時，一個 `switch` 就夠 |
| Strategy（權限規則） | 「誰可以做」：擁有者、主管、財務 | 角色只有三種時，一個函式加 `enum` 就夠，不必每種角色一個類別 |
| Observer | 變體 3 的通知：狀態改變之後，由通知者決定誰收到什麼 | 只有一種通知、一個收件人時，直接呼叫就好 |

State 模式（每個狀態一個類別）在這題通常太重：狀態本身沒有行為，差別只在轉移和權限，一張表比八個類別清楚。說得出這個理由，比硬套 State 模式更好。

## 每個變體在考什麼

| 變體 | 考點 | 好的設計改哪裡 |
| --- | --- | --- |
| 1 大額財務審核 | 加一個狀態、一個依金額而定的轉移 | 轉移表多幾行，加上「條件」欄位；動作方法完全不動 |
| 2 主管代理 | 權限規則改變，歷史要記「代誰做」 | 只有權限檢查的那一個函式知道代理；代理關係另外放一個類別，不塞進組織圖 |
| 3 通知 | 狀態改變時的副作用 | 協調者在狀態改變後多呼叫一次通知者；誰收到什麼全在通知者裡 |

## 參考設計的改動數字

用 `ood` 量的，只算 src/。兩套參考設計都通過全部 30 個測試；格式是「既有類別 / 既有函式 / 改在既有類別和函式裡的程式碼行」。

| 變體 | 轉移表的設計 | 每個動作各寫一次的設計 |
| --- | --- | --- |
| 1 大額財務審核 | 2 / 2 / +6 −1 | 2 / 4 / +26 −11 |
| 2 主管代理 | 1 / 2 / +17 −7 | 2 / 3 / +19 −6 |
| 3 通知 | 2 / 2 / +6 −0 | 1 / 5 / +17 −0 |

- 變體 1 和 3 差最多：散開的寫法要改四到五個動作方法。
- 變體 2 兩邊差不多。權限檢查在好的設計裡本來就只有一個地方，但它的回傳值要從「可以／不可以」改成「可以，代誰」，所以那個函式整個重寫；散開的寫法則是 `approve` 和 `reject` 各改一次。這說明改動數字只在變動跨越職責邊界時才會拉開差距。
- 變體 3 好的設計新增的程式比較多（一個新的通知類別），但幾乎不動既有程式；散開的寫法新增得少，卻要改五個方法。看「既有」的數字，不要只看總行數。

## 各職級的強弱設計（研究報告第 5.3 節）

| 職級 | 弱 | 強 |
| --- | --- | --- |
| 初階 | 狀態用字串到處比較，權限檢查漏了「不能核准自己的單」 | 狀態是 `enum`，五個動作能正確實作，錯誤碼順序對 |
| 中階 | 每個動作各寫一套檢查；被問「加一個狀態」時說要改每個方法 | 轉移集中在一處；能說出加一個狀態要改哪幾行 |
| 高級 | 一開始就做了通用的工作流程引擎、可設定的角色系統，35 分鐘寫不完 | 先用最小的轉移表過核心，被連問三個「如果……」時，每次都指得出只改哪一兩個地方，並說明為什麼代理關係不放進組織圖 |

## 面試時可以主動講的

- 「狀態沒有自己的行為，所以我用轉移表，不用每個狀態一個類別。」
- 「先查狀態再查權限，這是規格要求的順序；我把它寫在唯一的一條路上。」
- 「通知是副作用，我讓工作流程發出『狀態改變了』，由別的類別決定通知誰。」
