# AI 輔助程式回合練習包（VS Code、Windows 11）

這個練習包把[研究報告](../beyond-dsa.zh-TW.md)第 6.6、6.7 節的建議做成可以照著走的練習。結構模仿 Meta AI 回合的三個階段：在一個你沒寫過的多檔案程式庫裡，先修 bug，再實作功能，最後在大資料下優化。

- **6 個原創情境**：每個都是一套多檔案的 C++ 程式庫，有 README、既有程式、既有測試，以及三個階段的題目和測試。情境是為這個專案寫的，不是任何公司的考題。第 2、3 階段需要的資料結構各不相同：heap 驅動的模擬、滑動視窗、有序集合、trie、union-find，以及每個團隊一個 heap 的穩定配對。
- **`drill` 練習工具**：用 C++ 寫成。它一次只揭曉一個階段，替每個階段計時；本階段的測試通過才能前進（時間到了也可以跳過）；結束時要寫完複盤，這次練習才會記錄下來。
- **只需要裝三樣東西**：VS Code、C/C++ 擴充、WinLibs GCC，跟 [cpp-practice](../cpp-practice/README.zh-TW.md) 一樣。另外再加上你要練的 AI 助手，例如 Copilot、Claude Code 或 Cursor。有 Git 的話會用來顯示你改了什麼，但不是必要的。

## 1. 先讀這段：練習包怎麼幫你

左欄是研究報告的建議，右欄是練習包怎麼逼你做到。

| # | 要點 | 為什麼 | 練習包怎麼做 |
| --- | --- | --- | --- |
| 1 | **在沒寫過的程式庫裡練** | Meta、Google、Chakra 的 AI 回合，給的都是現成的多檔案程式庫，不是空白的函式 | 每個情境都是完整的小專案：資料夾結構、README、既有測試，也有一個藏著的 bug |
| 2 | **一次只看一個階段** | 正式面試的題目是逐步給的，先看到後面的題目會讓第 1 階段失真 | `drill next` 才揭曉下一階段的題目和測試。後面的題目和複盤要點都放在練習資料夾外面，主視窗也隱藏了 `scenarios/` |
| 3 | **照階段計時，時間到就往下** | Meta 的回合是 60 分鐘，扣掉開場，實作和優化大約只剩 30 到 40 分鐘 | 每次測試之後都會顯示各階段的用時；超過建議時間就提醒你用 `--skip` 往下走 |
| 4 | **AI 只看得到這次的程式庫** | AI 讀得到解答或後面的題目，練習就沒有意義 | 每次練習都是獨立的資料夾（也是獨立的 git repo），要用新視窗打開。`AGENTS.md`、`CLAUDE.md`、`.github/copilot-instructions.md` 會告訴 AI 這次的規則 |
| 5 | **練不同的 AI 規則** | Meta 的 AI 只能在聊天面板回答；Canva 和 Chakra 讓你用自己的工具 | 三種模式：`chat`（只用聊天，程式碼自己打）、`open`（任何工具都行）、`none`（不用 AI，量自己的基準） |
| 6 | **先講方案，再下 prompt** | 各家評分都看你有沒有主導 AI，而不是被 AI 帶著走 | 第 2 階段的題目要求你在 prompt 之前，先說出資料結構和複雜度 |
| 7 | **先量測再優化** | 第 3 階段最常見的錯，是沒量測就猜 | 每個大型測試的資料形狀都不一樣。有四個情境的瓶頸在你沒寫過的程式裡；另外兩個情境，既有的程式只有在你選擇沿用時才會慢。用猜的會改錯地方 |
| 8 | **太慢就直接停** | O(n²) 的寫法可能跑好幾分鐘 | 每個大型測試在超過上限 3 倍時就會被停掉，並標記為逾時。每個大型測試各自在獨立的行程裡跑，所以堆疊溢位也會被報告出來，不會中斷其他測試 |
| 9 | **寫下複盤才算數** | 回放檢查（第 6.7 節）的三件事：prompt 之前有沒有先講方案、AI 的每段產出有沒有執行驗證、AI 寫錯時多久發現 | `drill done` 會產生 `REVIEW.md`，四個必填欄位沒寫完，就不記錄這次練習 |
| 10 | **做完才看要點** | 先看要點等於先看解答 | 複盤要點在 `drill done` 之後才會複製到練習資料夾 |

## 2. 安裝

1. 安裝 [VS Code](https://code.visualstudio.com/)。
2. 用 Windows 11 內建的 winget 安裝 WinLibs GCC。已經為 cpp-practice 裝過的話就跳過這步。

   ```bash
   winget install --id BrechtSanders.WinLibs.POSIX.UCRT --exact
   ```

3. **重新開啟 VS Code**，讓新的 PATH 生效。接著用「檔案 → 開啟資料夾」打開 `ai-round-practice` 這個資料夾（不是整個 repo）。
4. VS Code 會提示安裝建議的擴充 **C/C++**（`ms-vscode.cpptools`），裝這一個就好。
5. 準備好你要練的 AI 助手。練 `chat` 模式時，如果你用的是會直接改檔案的工具，請切到只回答、不改檔的模式，例如 Copilot Chat 的 Ask。

第一次執行任何 `drill:` 工作時，會自動建置 `build/drill.exe`，約 10 秒。

## 3. 一次練習的流程

主視窗（`ai-round-practice`）只用來開始練習，題目在新視窗裡做。

| 步驟 | VS Code | 終端機 |
| --- | --- | --- |
| 1. 開始 | 主視窗執行工作「drill: 開始新的練習」，選情境和模式。工具會建立 `work/<情境>-<時間>/`，並用新視窗打開。 | `.\build\drill.exe start build-planner --mode chat` |
| 2. 先讀，不要急著改 | 讀 `TASK.md`，再看 `README.md`、`src/`、`tests/` | |
| 3. 跑測試 | **Ctrl+Shift+B** | `drill test` |
| 4. 進到下一階段 | 工作「drill: 下一階段」。時間到了，改用「drill: 跳過並前往下一階段」。 | `drill next`、`drill next --skip` |
| 5. 第 3 階段只跑大型測試 | 工作「drill: 只跑大型測試」 | `drill test . large` |
| 6. 看時間 | 工作「drill: 狀態」 | `drill status` |
| 7. 程式崩潰或要逐步追蹤 | **F5**，選「除錯測試」 | `drill debug` |
| 8. 結束 | 工作「drill: 結束並複盤」執行兩次：第一次會停錶並產生 `REVIEW.md`；填完四個欄位後再執行一次，才會記錄並顯示複盤要點 | `drill done` |

在練習資料夾的終端機裡，`drill` 指的是主視窗的 `build/drill.exe`。直接用工作最方便，因為工作裡已經寫好完整路徑。

**時間建議。** 第 1 階段約 15 分鐘（含閱讀程式庫），第 2 階段約 25 分鐘，第 3 階段約 15 分鐘，最後 5 分鐘收尾和討論。

**要錄下來。** 用 Windows 內建的「剪取工具」錄螢幕，或 Xbox Game Bar（Win+G），一邊做一邊講話。之後回放時檢查第 1 節第 9 項的三件事。用 `git diff` 可以看到這次改了哪些地方。

## 4. 六個情境

| 情境 | 程式庫在做什麼 | 第 1 階段 | 第 2 階段 | 第 3 階段 |
| --- | --- | --- | --- | --- |
| `build-planner` 建置排程器 | CI 用的建置清單工具：解析清單、排出建置順序、算關鍵路徑 | 報表的時間不對 | 模擬多台機器平行建置 | 最多 22 萬個目標，三種不同形狀的清單 |
| `log-alerts` 日誌告警 | 值班用的日誌工具：合併多個服務的日誌、產生摘要 | 合併後的時間線順序錯了 | 依規則發出告警 | 每份約 40 萬筆事件，三種不同形狀 |
| `room-booking` 會議室分配 | 辦公室的會議室工具：檢查人工預約的衝突 | 報出不存在的衝突 | 自動分配會議室 | 5,000 到 12,000 間會議室、15 萬到 20 萬筆請求，三種不同形狀 |
| `api-gateway` API 閘道路由 | API 閘道的路由工具：正規化請求路徑、產生流量報表 | 報表裡的路徑被拆錯、被截短 | 依最具體的路由轉送請求，並回 404 或 405 | 最多 40,400 條路由、30 萬個請求，三種不同形狀，其中一種是掃描器送來的超長路徑 |
| `netlist-check` 電路板連線檢查 | 硬體團隊的電路板工具：讀取線路表、產生腳位報表 | 報表漏列沒接的腳位 | 比對佈線，找出斷路和短路 | 最多 64 萬支腳位、16 萬個網路、24 萬個 via，三種不同形狀的板子 |
| `team-match` 實習生分組配對 | 實習計畫的配對工具：讀取志願和面試分數、產生需求報表 | 平均相同的人排錯順序 | 依志願和團隊的排名，把實習生分到團隊 | 最多 11 萬個實習生、6,000 個團隊、72 萬筆面試紀錄，三種不同形狀 |

每個情境有 4 到 6 個模組（各一個 `.hpp` 加 `.cpp`），外加一個命令列程式。測試數：第 1 階段 6 到 10 個，第 2 階段 7 到 8 個，第 3 階段 3 個。每個情境的題目都用英文寫，跟正式面試一樣；複盤要點用中文。

**放進 12 週計畫的方式**（研究報告第 7.2 節的「AI 輔助」欄）：

| 週 | 練習 |
| --- | --- |
| 3–4 | `build-planner`，`chat` 模式 |
| 5–6 | `log-alerts`，`chat` 模式 |
| 7–8 | `room-booking`，`open` 模式；換一個比較弱的模型 |
| 9 以後 | 改用自己挑的開源專案（第 5 節）。如果目標公司有提供練習環境，例如 Meta 的練習題，優先用它。 |

同一個情境重做時，bug 和解法你都已經知道了。所以重做只拿來練別的東西，例如換成 `none` 模式量自己的基準，或專門練「邊做邊講」。

後來加的三個情境（`api-gateway`、`netlist-check`、`team-match`）用的是不同的資料結構。一週有時間做第二次練習時加做一個，或在第 9 週換成開源專案之前先做。

## 5. 自己帶程式庫

練習包的情境做完之後，用真的開源專案練習。

1. 挑一個沒看過、有測試、能在你電腦上建置的小專案，最好在幾千行以內。
2. 請朋友，或另一個 AI 對話，在程式裡埋一個 bug，並且不要看它改了什麼。可以用這段提示：

   ```
   In this repository, introduce one subtle bug of the kind found in code review:
   a wrong type conversion, an off-by-one, or an inverted condition. Make at least
   one existing test fail. Do not tell me where it is. Commit it with the message
   "practice bug" and do not show me the diff.
   ```

3. 第 2 階段：從它的 issue 清單挑一個小功能，或自己定一個。
4. 第 3 階段：把輸入放大 100 倍，找出瓶頸。
5. 計時用手機。複盤時，把任何一個練習資料夾裡的 `REVIEW.md` 拿來當範本。

## 7. 已驗證

在 Windows 11 上用 WinLibs g++ 16.2.0 驗證過以下各點。參考解答沒有放進專案。

- **原始程式庫一定會失敗。** 每個情境的原始程式庫，第 1 階段都有測試因為藏著的 bug 而失敗（build-planner 2 個、log-alerts 2 個、room-booking 1 個、api-gateway 2 個、netlist-check 2 個、team-match 2 個），第 2 階段的測試全部失敗。
- **參考解答通過全部測試。** 大型測試用時 0.08 到 0.46 秒，上限是 1 到 1.5 秒。
- **第 2 階段的答案由不同寫法交叉核對過。** 每個情境的第 2 階段，期望值都是用 2 到 3 種獨立寫法算出來的，結果一致。後來加的三個情境，第 3 階段的期望值也用另一種獨立寫法重算過，結果一致。
- **較慢的寫法會在第 3 階段失敗。** 每種都至少有一個大型測試失敗，原因是逾時、堆疊溢位，或超過上限 1.3 到 2.3 倍：

| 情境 | 較慢的寫法 | 結果 |
| --- | --- | --- |
| build-planner | 每個事件都掃描全部目標、用遞迴算 tail | 一個大型測試逾時，一個堆疊溢位 |
| build-planner | 既有程式碼中，去除重複依賴的寫法 | 只有扇入的大型測試逾時 |
| log-alerts | 每筆事件往回掃描視窗 | 熱點的大型測試逾時 |
| log-alerts | 全域掃描 | 三個大型測試全部逾時 |
| log-alerts | 既有的合併寫法 | 只有四檔交錯的大型測試逾時 |
| room-booking | 五種部分改進的寫法 | 依寫法不同，1 到 3 個大型測試超時（1.3 到 2 倍以上），詳細數字在該情境的複盤要點 |
| api-gateway | 每個請求檢查全部路由、依第一段分桶、trie 但 405 逐條檢查 | 依寫法不同，1 到 2 個大型測試逾時 |
| api-gateway | 既有的路徑正規化（`collapse_slashes`） | 只有掃描器流量的大型測試逾時 |
| netlist-check | 遞迴 DFS | LED 面板和接地平面的大型測試堆疊溢位 |
| netlist-check | 沒有路徑壓縮的 union-find、每個網路各做一次 BFS、每個區塊都掃描全部網路 | 依寫法不同，1 到 2 個大型測試失敗，至少一個逾時 |
| netlist-check | 既有的 via 雜湊（只看名稱的前 4 個字元） | 只有接地平面的大型測試逾時 |
| team-match | 每次申請都重新排序、線性搜尋名次、同步回合、每次從頭找沒被分配的人、沿用既有的 `rank_applicants` | 依寫法不同，1 到 3 個大型測試逾時或超時（1.6 到 2.3 倍），詳細數字在該情境的複盤要點 |

- **`drill` 的完整流程跑過**：建立練習包時跑過一次；後來加的三個情境也各跑過一次，分別用 `chat`、`open`、`none` 模式。流程是：開始 → 第 1 階段失敗 → 修好 → 前進 → 第 2、3 階段 → 執行程式 → 除錯版建置 → 複盤檢查與紀錄。修改一個檔案時只會重新編譯那個檔案；修改標頭檔時會全部重新編譯。

時間上限是依這台電腦設定的，參考解答至少有 3 倍的餘裕。如果你的電腦明顯比較慢，參考解答的時間也會跟著變長。

## 8. 疑難排解

| 症狀 | 處理 |
| --- | --- |
| 找不到 `g++` | 裝完 WinLibs 後要重開 VS Code。在終端機執行 `where g++` 確認。 |
| 新視窗沒有自動打開 | `code` 不在 PATH 上。手動用「檔案 → 開新視窗」，再打開 `drill start` 印出的資料夾。 |
| 大型測試顯示 `TLE ... Stopped` | 測試超過上限 3 倍，被停掉了。這通常代表複雜度不對，不是常數太大。 |
| 顯示 `crashed with exit code -1073741571` | 堆疊溢位，通常是遞迴太深。按 F5 用除錯版重跑。 |
| 中文變亂碼 | 在終端機先執行 `chcp 65001`。 |
| 改了 `tools/drill.cpp` | 主視窗執行工作「drill: 重新建置工具」 |
| 不想要某次練習了 | 直接刪掉 `work/` 底下那個資料夾。紀錄在 `progress/sessions.tsv`，要刪也可以直接刪。 |
| Linux 或 macOS | `drill` 和測試框架的程式碼有處理這兩個平台，但沒有實際測試過。macOS 除錯要把 `MIMode` 改成 `lldb`。 |
