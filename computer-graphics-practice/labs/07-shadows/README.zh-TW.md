# 實驗 07 — 陰影與影像品質

[English](README.md) | **繁體中文**

## 目標

加入第一個需要多個繪製階段的效果。先從光源把場景深度繪製到貼圖，再讓攝影機的每個取樣點把自己與光源的距離和這張陰影貼圖比較。把偏移的取捨變成看得見的現象（陰影痤瘡與陰影分離），用 PCF 濾波陰影查詢，並以相同放大倍率比較三種抗鋸齒做法。最後要能說明每項品質設定的成本，以及你如何量測。

```
階段 1  陰影    世界 --V_light、P_light（正交）--> 深度測試 --> 陰影貼圖（深度貼圖）
階段 2  攝影機  世界 --V、P-----------------------> 深度測試 --> 色彩目標（每像素 1 或 4 個取樣點）
                世界 --B · P_light · V_light--> (u, v, d)    照亮 = d − 偏移 ≤ map(u, v)，再對各次取樣平均
階段 3  輸出    色彩目標 --在線性光中平均取樣點--> linearToSrgb --> canvas
```

## 執行

開啟 `../../index.html`，選擇 **07 · 陰影**。在畫布上拖曳可環繞；不拖曳直接點一下可移動放大鏡（橘色方框）。左側放大鏡固定顯示有鋸齒的對照版：每像素 1 個取樣點、1 次最近紋素的陰影取樣；右側顯示目前設定。兩者都以 12 倍顯示同一批 40 × 27 像素。「顯示」選單可把著色結果換成陰影係數、陰影貼圖紋素格線、深度差，或陰影貼圖本身。頁面需要 WebGL 2，但不需要伺服器或網路連線。

GPU 耗時讀數使用 `EXT_disjoint_timer_query_webgl2` 擴充。若瀏覽器沒有提供，讀數會顯示破折號；改量什麼請見 H 題。

## 閱讀實作

1. **場景。** 地面、立方體、球體與細柱子，由 `../common/mesh.js` 依實驗 06 的 32 位元組頂點格式建立。每個物體都放在地面上，因為接觸點是陰影分離最先出現的地方。
2. **光源的攝影機。** `lightFrame` 沿光線方向 L，在距離場景 `LIGHT_DISTANCE` 單位處放一台攝影機，並給它一個正交方框（`../common/math.js` 的 `orthographic()`）：平行光的光線彼此平行，因此沒有透視。「光源方框半寬」決定方框涵蓋多少世界範圍，也就決定一個陰影貼圖紋素（texel）有多寬。近、遠裁切面包住場景外的一個球；兩者的距離就是偏移所用的深度範圍。
3. **繪製至貼圖。** `../common/webgl.js` 的 `webgl.depthTarget` 建立一張 `DEPTH_COMPONENT24` 貼圖，以及唯一附件就是這張貼圖的影格緩衝區。`shadowPass` 綁定它、把視口設為貼圖大小、把深度清除為 1，再用只轉換位置的頂點著色器和什麼都不寫的片段著色器畫出每個物體：深度測試會為每個紋素保留最近的深度。「陰影階段剔除」決定要存哪些面。
4. **從世界座標到陰影貼圖座標。** `shadowMatrix = B · P_light · V_light`，其中 `NDC_TO_TEXTURE`（B）把 NDC [−1, 1]³ 映射到 [0, 1]³。頂點著色器在 `gl_Position` 之外再輸出 `vShadowCoord = shadowMatrix · world`，光柵器會像其他 varying 一樣插值它。
5. **比較。** 深度貼圖設定為 `TEXTURE_COMPARE_MODE = COMPARE_REF_TO_TEXTURE`、比較函式為 `LEQUAL`，所以片段著色器透過 `sampler2DShadow` 讀取：`texture(uShadowMap, vec3(uv, reference))` 在 `reference ≤ 已存深度` 時回傳 1，否則回傳 0。使用 `NEAREST` 濾波時只比較一個紋素；使用 `LINEAR` 時，硬體會比較最近的 4 個紋素，再混合這些 0／1 結果（「每次取樣的比較」）。另一個關閉比較的取樣器物件（`webgl.rawDepthSampler`）則把同一張貼圖當成一般深度讀取，供除錯檢視使用。
6. **偏移。** `depthBias(n)` 回傳 `constant + slope · texelDepth · tan θ`，其中 θ 是法線與 L 的夾角，`texelDepth` 是一個紋素寬度除以深度範圍。背向光源傾斜的表面，從一個紋素到下一個紋素，深度會改變 `紋素寬度 · tan θ`，所以斜率項表示要容忍幾個紋素份量的這種變化。固定項以整個光源方框的深度單位計算（這裡 0..1 對應 18 個世界單位）。讀數會把兩項都換算成世界單位。
7. **PCF。** `shadowFactor` 以間隔一個紋素的 1 × 1、3 × 3 或 5 × 5 取樣格，逐一和同一個參考深度比較，再平均結果：這就是 PCF（percentage-closer filtering，先比較再平均）。若先平均深度再比較一次，邊緣又會變硬。
8. **抗鋸齒。** canvas 本身沒有深度緩衝區，也不抗鋸齒。攝影機階段一律畫進 `webgl.colorTarget` 建立的螢幕外 `SRGB8_ALPHA8` 目標；寫入時把線性值編碼成 sRGB，取樣時再解碼。
   - **關閉：** 每像素 1 個取樣點。
   - **MSAA 4×：** 多重取樣渲染緩衝區。涵蓋範圍與深度在每像素 4 個取樣位置測試，但每個三角形在每個像素只執行一次片段著色器。`webgl.resolve`（`blitFramebuffer`）把取樣點平均成單一取樣的貼圖。
   - **SSAA 2 × 2：** 寬高都是兩倍的目標。包含陰影查詢在內的所有運算，每像素都執行 4 次，再由 `presentPass` 在線性光中平均每個 2 × 2 區塊。

   接著 `presentPass` 用 `linearToSrgb` 編碼一次，寫入 canvas。
9. **放大鏡。** `render` 先只在放大鏡範圍內（`gl.scissor`）畫出對照版，用 `readPixels` 讀回這些像素，並像實驗 05 一樣翻轉列順序。接著以目前設定畫滿整個 canvas，再讀一次同一批像素。最後一個讀數顯示兩者中心像素的 sRGB 值。
10. **成本。** 記憶體與工作量讀數由設定計算而來。GPU 耗時讀數用計時查詢包住陰影階段，以及攝影機與輸出階段；對照版不計時。在 WebGL 呼叫前後用 `performance.now()` 只量得到 JavaScript 執行緒（實驗 05 的檢核問題 5）。

刻意留給你的部分：光源方框不會跟著攝影機、偏移只存在於著色器中、每次 PCF 取樣都和中心點的深度比較、只有平行光，以及貼圖固定為 24 位元。`TODO(exercise …)` 註解標出各項修改的位置。

## 慣例

本實驗依循 [`../../CONVENTIONS.zh-TW.md`](../../CONVENTIONS.zh-TW.md)，並新增一項：陰影貼圖的查詢方式。

- **WebGL：** `(u, v, d) = 0.5 · ndc + 0.5`，不翻轉 y。繪製至貼圖時，視窗第 0 列（最下面一列）會寫進貼圖的 v = 0 列，所以 `v = 0.5 · y_ndc + 0.5` 讀回的正是當初寫入的紋素。d 與儲存的視窗深度使用相同的 `(z_ndc + 1) / 2` 映射，兩者才能比較。
- **Direct3D 12：** NDC z 本身就是儲存的深度，所以 `d = z_ndc`。NDC y = +1 落在第 0 列，也就是 v = 0，所以 `v = 0.5 − 0.5 · y_ndc`。
- **Vulkan：** 同樣 `d = z_ndc`。若陰影階段不翻轉 y，NDC y = −1 落在第 0 列，`v = 0.5 + 0.5 · y_ndc`；若使用第二部為了讓畫面變正的負高度視口，則 `v = 0.5 − 0.5 · y_ndc`。寫入與讀取陰影貼圖要用同一條規則。
- **色彩目標**是 `SRGB8_ALPHA8`：著色器寫入線性光，GPU 在寫入時編碼、取樣時解碼，輸出階段為 canvas 編碼一次。MSAA 解析時如何平均 sRGB 取樣點由實作決定；G 題會檢查這一點。

## 練習

- **A — 法線偏移：** 在投影到陰影貼圖之前，先沿表面法線移動查詢點：`world + n · k · 紋素寬度`，k 約為 1。可以在頂點著色器中做（偏移要乘上 `uShadowMatrix` 的那個位置），或把世界座標與矩陣傳到片段著色器。把斜率偏移設為 0，在光源仰角 10° 時，和只用深度偏移的版本比較陰影痤瘡與立方體的接觸陰影。哪一種讓陰影更貼近立方體？為什麼？
- **B — 多邊形偏移：** 在 `shadowPass` 中用 `gl.enable(gl.POLYGON_OFFSET_FILL)` 與 `gl.polygonOffset(factor, units)` 把偏移移到陰影階段，並把兩個偏移滑桿都設為 0。哪個參數扮演斜率項、哪個扮演固定項？為什麼 `units` 以「可分辨的最小深度差」為單位，而不是世界單位？和實驗 04 的 F 題比較。
- **C — 貼合並穩定光源方框：** 改由攝影機計算方框，而不是用滑桿：把攝影機視錐（在某個最大距離截斷）的角點轉換到光源視圖空間，取它們的範圍，並印出得到的紋素寬度。接著比較兩種閃爍：在 128 紋素時開啟「光源繞行」（紋素格線隨光源旋轉），以及用貼合後的方框環繞攝影機（格線以不到一個紋素的距離滑動）。把方框中心在光源空間中對齊到整數個紋素。這能消除哪一種閃爍？為什麼另一種不行？
- **D — PCF 需要更多偏移：** 把斜率偏移設為 1，在「只顯示陰影係數」下比較 1 次取樣、PCF 3 × 3 與 PCF 5 × 5。用偏移讀數的最後一行，解釋為什麼較大的取樣範圍會出現陰影痤瘡。然後在不加大偏移的前提下修正它：用 `dFdx` 和 `dFdy` 取得陰影座標在螢幕空間的導數，解出 d 在 u、v 方向每個紋素的變化量，讓每次取樣都有自己的參考深度（receiver-plane depth bias）。
- **E — 聚光燈：** 用 `perspective()` 與光源位置取代正交光源。查詢時需要除以 w（或使用 `textureProj`），紋素寬度會隨與光源的距離變大，而儲存的深度也不再與距離成線性關係。哪一個偏移項必須修改？要怎麼改？
- **F — 16 位元陰影貼圖：** 以 `DEPTH_COMPONENT16` 搭配 `UNSIGNED_SHORT` 配置陰影貼圖。把斜率偏移設為 0、光源仰角設為 90°，分別找出 24 位元與 16 位元時能消除痤瘡的最小固定偏移。把它們與 18 單位方框的一個深度步距對照；紋素讀數會顯示 24 位元的步距。
- **G — 在錯誤的色彩空間解析：** 在 `PRESENT_FRAGMENT_SHADER` 中，先用 `linearToSrgb` 編碼每個紋素，再平均編碼後的值，最後不再編碼。在 SSAA 下把放大鏡對準球體在深色背景前的輪廓，比較中心像素的數值。接著在同一個像素切到 MSAA：這個瀏覽器對 `SRGB8_ALPHA8` 渲染緩衝區的解析，是在線性光中平均的嗎？
- **H — 量測成本：** 一次只改一項設定（陰影貼圖大小、取樣次數、每次取樣的比較、抗鋸齒），記錄兩個階段的 GPU 耗時。哪項成本隨陰影貼圖紋素數增加？哪項隨螢幕像素 × 取樣點數增加？哪項隨每個著色取樣點的陰影取樣次數增加？若計時讀數顯示破折號，就在每個影格把攝影機階段畫 N 次，逐步加大 N 直到影格率低於螢幕更新率，再比較各設定下的 N。寫下一個瓶頸假設，以及一個可能推翻它的量測。

## 檢核問題

在實驗筆記中回答：

1. **陰影痤瘡。** 根據你的截圖，解釋被照亮的表面為什麼會遮到自己。在深度差檢視中，為什麼正負號在幾個像素內就會翻轉？為什麼圖樣會隨光源角度與貼圖大小改變？
2. **陰影分離。** 寫出造成陰影分離（peter-panning）的偏移值，以及陰影離開投影物多遠。為什麼足以應付掠射光的固定偏移，會讓接觸點的陰影分離？你最後選了哪一組偏移值？搭配哪一種取樣範圍？
3. **兩個階段。** 追蹤地面上一個點經過兩個階段：世界 → 光源視圖 → 光源裁切 → NDC → (u, v, d) → 紋素 → 比較。哪個矩陣把 NDC 映射到貼圖座標？為什麼 WebGL 在這裡不需要翻轉 y？換到 Direct3D 12 時要改什麼？
4. **相同放大倍率下的邊緣。** 比較對照版與濾波後的輪廓邊緣和陰影邊緣。哪個設定讓哪種邊緣變平滑？為什麼 MSAA 無法讓陰影邊緣平滑，SSAA 卻可以？
5. **成本與品質。** 寫出每項品質設定的成本：記憶體、每個著色取樣點的陰影取樣次數、每像素取樣點數、每像素著色次數。你的量測顯示哪一項在你的 GPU 上最昂貴？和依數量推估的結果一致嗎？

## 之後會在哪裡用到

- **引擎：** 第二部的引擎路線會把本實驗擴展成串接式陰影貼圖（E4）：每個距離範圍一個光源方框，加上 PCF、串接區間混合，以及對齊紋素以抑制閃爍。時間性抗鋸齒（E5）把 SSAA 額外的取樣點分散到多個影格；E7 則比較陰影貼圖與光線追蹤陰影。
- **合成器：** 向量路徑與文字（T1–T3）不是靠增加取樣點抗鋸齒，而是計算圖形涵蓋每個像素的比例。視窗特效就是繪製至貼圖的階段，而抗鋸齒邊緣的混合，也和這裡的解析一樣必須在線性光中進行。
