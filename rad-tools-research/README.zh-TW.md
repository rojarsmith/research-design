# RAD tools 不同領域、產品規模的研發難度與資源門檻

研究日期：2026-10-21。範圍是整體工具產業；代表產品用於辨認技術責任，不代表推薦、效能排名或任何公司的研發投入。

## 1. 核心結論

**小團隊有機會做出聚焦的 RAD 商用品，但必須限制領域、執行環境與支援範圍。通用平台的門檻，主要來自讓使用者建立的程式長期、可靠、安全地運作。** 拖拉畫布只是入口，後面還有資料模型、執行語意、除錯、部署、舊專案升級、連接器與維護責任。

本研究的工程推論如下；數字是規劃情境，並非實測或廠商公開的人力統計：

| 欲交付的規模 | 建議起始資源情境 | 真正要證明的事 |
| --- | --- | --- |
| 聚焦原型 P0 | 1–3 人、2–4 個月 | 一條從建立、儲存到執行的完整路徑可行；不足以宣稱商用 |
| 小型商用品 P1 | 4–8 人、9–18 個月 | 外部使用者可自行交付、專案可升級、錯誤能定位、可維護 |
| 成熟平台 P2 | 15–40 人、24–48 個月以上 | 多團隊、多版本、多部署及擴充生態能持續維運 |

這是共用基線，不是所有領域套用同一工期。自製編譯器、多平台原生框架、工業協定、圖形資料流程編譯或完整遊戲引擎，可能需要更大且持續多年的投入。各領域範圍見[資源模型](research/02-resources.zh-TW.md)。

較低的起步門檻通常是：在既有 Web／UI runtime 上做範本式建站、受限 CRUD 或單一協定的流程工具。嵌入式工具若只支援一個 SDK 與一塊板也能縮小，但多板、多 SDK、效能與硬體驗證會提高門檻。企業通用平台、工業監控與量測環境的困難，則包含交易／狀態一致性、可靠度、設備及長期支援。

## 2. 研究問題與邊界

RAD 是 **Rapid Application Development**。此處研究能透過視覺設計、元件、資料模型、流程或程式產生加速應用開發的工具，涵蓋傳統 RAD IDE、low-code、部分 no-code 與領域型視覺工具。它們不是完全相同的產品類別，因此比較的是共同工程責任及領域差異。

主軸為「研發 RAD 工具產品」，另在第 7 節說明「使用工具開發應用」。產品規模也不等於客戶公司大小、畫面數、使用者數或市場營收：本研究以**功能廣度、部署責任、相容年限及生態承諾**定義 P0／P1／P2。沒有對市場規模 TAM 做金額估計。

研究假設團隊熟悉目標技術、可採用既有框架／資料庫／建置工具，初期只有一個主要領域，不自行重做所有基礎設施。人數為平均全職當量 FTE；「能運作的展示」「有人願付費試用」「成熟平台」分開驗收。

## 3. 十個領域的工程比較

下列是**本研究評分**。1 為既有元件即可完成的局部功能，3 為需要專責子系統與整合驗證，5 為跨層核心技術及長期相容責任；2、4 為中間值。分數用來暴露風險，不是量測值，也不加總成產品排名。P1 採既有引擎、範圍受限；P2 擴大部署、平台及支援承諾。

| 領域 | 代表或相鄰產品／基礎 | P1 難度 | P2 難度 | 最容易低估的責任 |
| --- | --- | --- | --- | --- |
| 桌面／原生視覺 IDE | Delphi／RAD Studio | 3–4 | 5 | 設計期與執行期元件一致、程式碼往返、多 OS／ABI |
| 網站／內容建構器 | GrapesJS 編輯器框架 | 2–3 | 4 | 專案模型、響應式版面、發布與還原 |
| 內部 CRUD／後台 | Appsmith、Retool | 3 | 4–5 | 資料來源、伺服器授權、憑證及環境隔離 |
| 行動／跨平台 App builder | FlutterFlow | 3–4 | 5 | 原生套件、簽署、離線同步、輸出程式碼相容 |
| 企業模型驅動平台 | Mendix、Power Apps | 4 | 5 | 模型與 runtime、資料遷移、交易及 ALM |
| 工作流程／整合工具 | Node-RED、n8n | 3 | 5 | 持久化、重試、冪等、外部 API 變動及可觀測性 |
| 嵌入式／MCU HMI | Qt Design Studio；LVGL 為圖形基礎 | 3–4 | 5 | 記憶體、字型、SDK／板級整合、預覽與真機差異 |
| 工業 HMI／SCADA | Ignition | 4 | 5 | tag 品質、斷線、告警、歷史與備援狀態 |
| 測試／量測資料流程 | LabVIEW | 4 | 5 | 型別與執行語意、儀器驅動、時間及數值正確性 |
| 遊戲／互動內容編輯器 | Godot 編輯器與外掛 | 3–4 | 5 | 資產匯入、場景、效能與多目標匯出 |

代表產品能力的來源與分類限制，見[領域詳解](research/01-domains.zh-TW.md)及[來源索引](research/04-sources.zh-TW.md)。遊戲、量測與 SCADA 為鄰近的領域型快速開發環境；LVGL 是 runtime 圖形函式庫、GrapesJS 是編輯器框架，不能當作完整商用 RAD 平台直接對照。

## 4. 為何產品愈大，工作不只增加元件數

1. **模型成為使用者資產。** 每個物件需要穩定 ID、型別、事件與引用規則。專案格式一旦交付，就有升級、復原及跨版本差異的責任。GrapesJS 文件特別區分編輯器的 project data 與 HTML／CSS 輸出，說明「產物」不等於「可完整編輯的專案」。[Storage Manager](https://grapesjs.com/docs/modules/Storage.html)
2. **執行責任不能由畫布代替。** Mendix 文件描述由 runtime 解譯模型，且其 patch runtime 與對應模型版本綁定。這支持版本管理是平台核心議題，不能據此推定其他產品也採同一機制。[Mendix Runtime](https://docs.mendix.com/refguide10/runtime/)
3. **多人交付需要完整生命週期。** Power Platform 文件將來源控制、環境、solutions 與 CI/CD 納入 ALM；Retool 也有分支、合併及部署管理。由此推論，商用工具需讓使用者管理變更，而非只提供編輯功能。[Microsoft ALM](https://learn.microsoft.com/en-us/power-platform/alm/overview-alm)、[Retool Source Control](https://docs.retool.com/source-control/guides)
4. **整合與部署帶來持續成本。** n8n queue mode 的 main、Redis、worker 與資料庫構成分散執行路徑；能加 worker 不等於第三方交易就自動達到 exactly-once。後者仍需個別設計與驗證。[n8n queue mode](https://docs.n8n.io/hosting/scaling/queue-mode/)

平台矩陣需要逐項算。例如 3 個 OS × 2 條 runtime 維護線 × 3 組 SDK × 2 種部署＝36 個候選組合；並非全部合法，也不是成本必然乘 36，但每一個宣稱支援的組合都需說明如何驗證與支援。

## 5. 團隊與資金如何估

P1 的 6 人情境可配置為：1 名架構／runtime、2 名編輯器／前端、1 名整合／建置、1 名 QA 自動化、1 名產品／UX／文件。安全、維運與客戶支援必須另有具名負責人，可由成員兼任或外援，但不能假設沒有工時。硬體、編譯或量測領域，必須補入相應的資深能力；不能用增加一般前端人數替代。

以下為**假設試算，不是薪資調查或廠商報價**：6 人 × 12 月 × 每 FTE 月新台幣 18 萬元完全人事成本＝1,296 萬元；加上工具、CI、雲端、設備及外部服務假設 150 萬元，再加 25% 預備金，合計 **1,807.5 萬元**。不含行銷銷售、稅務融資及規模化後的營運，也不等於已有足夠 runway 支撐收入形成。詳細區間、敏感度、維護編制及硬體成本見[資源與預算模型](research/02-resources.zh-TW.md)。

## 6. 建議進入順序與停止條件

資源尚未確定時，先做「一領域、一個 runtime、一條部署路徑」的 P0；使用既有 UI／流程／引擎，把差異放在領域模型、整合或可驗證的交付效率。選擇領域仍取決於團隊背景與實際客戶，並不存在所有團隊都適用的最容易市場。

建議 90 天依序驗證模型與存讀、實際執行、錯誤定位、乾淨環境建置及外部使用者獨立交付。若只能由作者操作展示、無法保存後等價重建、升版會破壞專案，或關鍵依賴的產品化權利尚未確定，就不宜直接擴大成通用平台。[里程碑與驗收](research/03-roadmap.zh-TW.md)列出測試情境與決策門檻。

AI 可作為產生受限模型或程式碼的入口，但是否降低總投入須以返工、驗證及支援成本量測。本研究不套用固定生產力折扣，也未測試任何 AI 系統的開發成效。

## 7. 若是「用 RAD 工具做應用」，門檻差在哪裡

| 應用情境 | 本研究的起始規劃假設 | 必須確認的限制 |
| --- | --- | --- |
| 單一團隊的小型表單／查詢工具 | 1–2 人、2–6 週 | 資料已可存取、既有身份系統、沒有複雜交易或同步 |
| 有多角色與外部整合的部門應用 | 2–5 人、2–6 月 | 資料品質、伺服器權限、環境遷移、連接器與授權 |
| 跨部門核心系統／設備產品 | 5–15 人、6–18 月以上 | HA、離線、資料遷移、硬體、稽核或長期支援需另估 |

以上不是保證值，未包含所有採購與組織等待。此時可把編輯器及部分 runtime 研發交給供應商，仍需負擔需求、領域邏輯、資料、整合與營運。購買成熟工具的訂閱費，不可直接與「自研同等平台」的人事成本比較；應以相同應用交付範圍與 3–5 年責任比較總持有成本。
