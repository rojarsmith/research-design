# 架構提案：MCU 上的單元匯流排與可程式化交換中心

提案日期：2026 年 11 月 19 日。狀態：**構想階段，尚未驗證**。本提案不受 EHS 現有設計限制；文中的延遲與記憶體目標都是假設，要靠第 11 節的驗證計畫確認。

## 1. 構想

在 MCU 上執行一條軟體匯流排。匯流排上有一個**可程式化的資訊交換中心**，各種**設備單元**掛在匯流排上：

- 有觸控功能的 GUI 是一個單元。
- 實體按鈕是一個單元，按下時觸發中斷，再透過匯流排送出事件。
- 感測器、Modbus 從站、MQTT 連線、馬達驅動、儲存都是單元。

單元之間不直接呼叫，只透過匯流排交換訊息。系統的行為由交換中心裡的規則決定，使用者以 Low Code 編寫這些規則。

```
 ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
 │ GUI 單元 │  │ 按鈕單元 │  │ Modbus   │  │ MQTT     │
 │ (觸控)   │  │ (中斷)   │  │ 感測單元 │  │ 雲端單元 │
 └────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘
      │ 事件/狀態    │ 事件        │ 狀態        │ 命令/狀態
 ═════╪═════════════╪═════════════╪═════════════╪═════════  單元匯流排
                          │
                 ┌────────┴────────┐
                 │ 可程式化交換中心 │  規則：觸發 → 條件 → 動作
                 └─────────────────┘
```

## 2. 判斷：值得做

| 面向 | 評價 | 理由 |
| --- | --- | --- |
| 技術可行性 | 高 | 有 Zephyr zbus、PX4 uORB、QP 等成熟先例（第 8 節） |
| 解決真實痛點 | 高 | 直接對應 [MCU 研發困擾排行](08-mcu-development-pain-points.zh-TW.md) 的前幾名，見下表 |
| 適合 Low Code | 高 | 「單元」與「規則」兩層，天然對應拖放與流程圖 |
| 差異化 | 中 | 匯流排本身不稀奇，差異化要靠 IDE：描述檔自動綁定、整機模擬、錄製重播、跨晶片透明 |
| 主要風險 | 需正面回答 | 即時性、中心瓶頸、小 MCU 的記憶體負擔（第 10 節） |

| MCU 研發痛點 | 單元匯流排的解法 |
| --- | --- |
| 並行與時序 bug 難以重現 | 單元之間的往來全部經過匯流排，**錄下匯流排就等於錄下系統行為**，可以重播、單步、比對 |
| 硬體還沒到、測試困難 | 任何單元都能換成模擬單元，交換中心的規則完全不用改 |
| 晶片綁定、BSP 移植 | 硬體細節封裝在單元內，換晶片只換單元的驅動 |
| 複雜度 | 單元只認識匯流排，不認識彼此；新增功能就是接上新單元 |
| 出貨後更新 | 交換中心的規則可以單獨更新，不必重燒整個韌體（第 5 節） |

## 3. 訊息模型

### 3.1 三種流量，不共用同一個管子

| 類型 | 例子 | 語意 | 傳遞方式 |
| --- | --- | --- | --- |
| **狀態**（State） | 溫度、電壓、開關位置 | 只保留最新值，新值覆蓋舊值；訂閱者讀快照 | 每個狀態一個固定槽位，不排隊 |
| **事件**（Event） | 按鈕按下、觸控點擊、告警、命令 | 不能遺失、保持順序 | 有上限的佇列；溢出策略在設計期宣告（拒收、丟最舊、上報錯誤） |
| **串流**（Stream） | framebuffer、音訊、影片、大檔案 | 高頻寬、大資料 | **不走匯流排**：留在單元內，或走專用通道，匯流排只傳控制訊息 |

GUI 單元是串流規則的最好例子：畫面繪製全部在單元內完成，匯流排上只有「按鈕 A 被點了」、「把溫度文字設成 25°C」這類語意層的訊息。

### 3.2 優先權

訊息分成至少三級：

| 級別 | 用途 | 規則 |
| --- | --- | --- |
| 緊急 | 告警、故障、急停通知 | 插隊；中心必須在有界時間內處理 |
| 一般 | 使用者操作、命令 | 先進先出 |
| 背景 | 遙測、日誌、雲端同步 | 可延遲、可合併 |

**安全相關的動作，例如急停，不經過可程式化的中心**，由硬體或單元自己保證。匯流排只負責通知。

### 3.3 位址

訊息以「單元實例 / 介面 / 成員」定位，例如 `button.start/press`、`sensor.tank1/temperature`、`gui.main/label_temp.text`。概念上對應 Matter 的 Endpoint、Cluster、Attribute 與 Event。建置時由 IDE 轉成整數 ID，執行期不比對字串。

## 4. 設備單元

### 4.1 描述檔

每個單元類型都有一份描述檔，宣告它的狀態、事件、命令與型別，類似 USB descriptor 或 Matter cluster。IDE 靠描述檔列出可綁定的資料、產生介面、在設計期做型別檢查。這是 Low Code 能成立的關鍵。

示意（格式待定）：

```yaml
unit: push_button
version: 1
config:
  pin: { type: gpio, required: true }
  debounce_ms: { type: u16, default: 20 }
events:
  press:   { payload: {} }
  release: { payload: { held_ms: u32 } }
  long_press: { payload: {}, after_ms: 800 }
states:
  pressed: { type: bool }
resources:
  isr: true
  ram_bytes: 32
```

```yaml
unit: modbus_rtu_sensor
version: 1
config:
  port: { type: uart, required: true }
  slave_id: { type: u8, required: true }
  poll_ms: { type: u32, default: 500 }
states:
  temperature: { type: f32, unit: degC, register: 30001 }
  online:      { type: bool }
events:
  timeout: { payload: { retries: u8 } }
commands:
  write_setpoint: { payload: { value: f32 }, register: 40001 }
```

### 4.2 單元的內部結構

```
┌──────────────── 單元 ────────────────┐
│  硬體驅動 / ISR ──▶ 單元內部邏輯 ──▶ 匯流排介面 │
│        ▲                               │      │
│        └──────── 命令 ◀────────────────┘      │
└──────────────────────────────────────┘
```

- 單元可以有自己的 Task，也可以是被動單元，由匯流排在呼叫端的情境中執行（類似 zbus 的 listener）。
- 硬即時迴路，例如馬達 PWM 或 ADC 取樣，**留在單元內部閉環**，匯流排只傳設定值與狀態。

### 4.3 中斷處理

中斷不直接進入交換中心：

1. ISR 只做最少的事：讀取硬體、清旗標、寫入事件槽位或推進佇列（中斷安全、無鎖）。
2. 匯流排在 Task 層取出事件、分派給中心與訂閱者，也就是 bottom half。
3. 按鈕去彈跳、長按判斷等邏輯在單元內完成，匯流排上只出現有意義的事件。

如此可以維持中斷延遲可預測，匯流排的負擔也不會進入 ISR。

## 5. 可程式化交換中心

### 5.1 規則模型

規則採「觸發 → 條件 → 動作」，與 ESPHome automation 的 trigger、condition、action 同構，對使用者容易理解：

```yaml
rule: start_cycle
on: button.start/press
if: sensor.tank1/online == true and sensor.tank1/temperature < 60
do:
  - send: motor.main/start { speed: 1200 }
  - set: gui.main/label_status.text = "Running"
else:
  - set: gui.main/label_status.text = "Check sensor"
```

規則可以用流程圖編輯，YAML 只是儲存格式。較複雜的邏輯可升級為狀態機（參考 Quantum Leaps QM），或者寫成程式碼區塊作為逃生口。

### 5.2 執行方式

| 方式 | 優點 | 缺點 | 適用 |
| --- | --- | --- | --- |
| 編譯成 C | 最快、最省資源、易做靜態分析 | 更新要重燒韌體 | 小 MCU、開發初期、安全要求高 |
| 位元碼 VM | 規則可以 OTA 熱更新，不動其他韌體 | 多占 RAM 與 Flash、較慢 | 需要出貨後改邏輯的產品 |

兩者可以並存：同一份規則先以 C 開發與驗證，量產時由專案決定要不要用 VM。熱更新的邏輯層是有人願意付費的能力，例子見 [動態語言 MCU 產品](06-dynamic-language-mcu-products.zh-TW.md) 的 Moddable 與 Toit。VM 設計可參考本 repo 的 [minilang 研究](../../dynamic-language-design-research/README.zh-TW.md)。

### 5.3 中心不能變成瓶頸

- 中心只做**路由與規則**，重計算交給單元。
- 每條規則的執行時間有上限，由 watchdog 監控；超時就中止並上報事件。
- 規則不可以直接呼叫硬體，只能經由匯流排送命令給單元。
- 中心本身可以分成多個執行情境（例如緊急規則與一般規則），避免低優先規則擋住高優先事件。

## 6. 靜態配置與資源

小 MCU 上預設**建置時靜態配置**：

- IDE 根據專案中的單元與規則，產生路由表、狀態槽位與事件佇列，全部是靜態陣列，不用動態記憶體。
- 每個單元在描述檔宣告資源需求，IDE 在設計期加總 RAM、Flash 與 CPU 預估，超出目標晶片就報錯。
- 執行期動態掛載單元只在資源較多的晶片上開放，並明確標示為進階功能。

## 7. 跨晶片

同一套匯流排協定可以經由 UART、CAN、SPI 或 USB 延伸到另一顆 MCU，或連到 PC 上的模擬器：

- **對使用者透明**：GUI 單元在顯示模組上、馬達單元在驅動板上，規則寫法不變。
- **橋接單元**：跨晶片的連線本身也是一個單元，負責序列化、重送與斷線事件。
- **對模組商的價值**：顯示模組本身就是匯流排上的一個 GUI 單元，主控板廠商只要接上匯流排，不必整合 UI。這和 EDT 的模組業務、以及串口屏市場的需求直接相關。

## 8. 先例比較

| 先例 | 相同點 | 不同點與可借用之處 |
| --- | --- | --- |
| [Zephyr zbus](https://docs.zephyrproject.org/latest/doxygen/html/group__zbus__apis.html) | Channel 加 observer 的發布與訂閱；observer 有同步 listener、非同步 subscriber，新版加入 async listener；由 VDED 分派通知 | 沒有單元描述檔、沒有可程式化中心、沒有 IDE。**可以直接當作 Zephyr 目標上的匯流排實作** |
| [PX4 uORB](https://docs.px4.io/main/en/middleware/uorb) | 飛控的發布與訂閱，所有模組經由 topic 溝通；同類感測器可多實例 | 每則訊息都要帶時間戳，logger 依此記錄；記錄完整速率的 topic 後可做[全系統重播](https://docs.px4.io/v1.12/en/debug/system_wide_replay.html)。**錄製重播的設計直接參考它** |
| [Quantum Leaps QP](https://www.state-machine.com/licensing) | Active Object 加事件發布與訂閱，每個物件有自己的佇列 | 理論成熟；規則升級為狀態機時可借用 QM 的建模方式 |
| [ESPHome](https://www.esphome.io/automations/actions) | 用 YAML 宣告元件，用 trigger、condition、action 串接，`lambda` 是 C++ 逃生口 | **最接近的 Low Code 先例**，但規則編譯進韌體、沒有匯流排抽象與錄製重播，且以 ESP 系列為主 |
| Matter 資料模型 | Endpoint、Cluster、Attribute、Command、Event | 可作為單元描述檔與位址的語意參考，未來也利於對接 Matter |
| IEC 61499 | 功能方塊加事件與資料連線 | 工控標準，理論最完整，但工具與學習成本高 |
| [MicroEJ](05-microej-comparison.zh-TW.md) | 多應用、隔離、應用層 OTA | 以 VM 容器為核心、Pro Code；本提案以靜態 C 為預設，VM 為選配 |

## 9. IDE 體驗（差異化所在）

| 能力 | 說明 |
| --- | --- |
| 單元庫 | 拖放單元到專案，依描述檔產生設定表單 |
| 規則編輯 | 流程圖或狀態機；自動補全只列出描述檔中合法的事件、狀態與命令 |
| 設計期檢查 | 型別檢查、未處理事件、無人訂閱的狀態、同一狀態有多個寫入者、資源超出晶片上限 |
| 整機模擬 | 所有單元都有模擬版本，在 PC 或 WASM 上跑完整系統；GUI 單元用真的 LVGL |
| 匯流排錄製與重播 | 真機透過除錯介面或 UART 回傳匯流排流量；在 PC 上重播、單步、時間軸檢視，並對應回規則的節點 |
| 混合模擬 | 部分單元在真機、部分在模擬器，例如真 GUI 加模擬馬達 |
| 匯出 | 產生純 C 加路由表；可選擇產生 VM 位元碼供 OTA |

## 10. 風險與對策

| 風險 | 說明 | 對策 |
| --- | --- | --- |
| 即時性被質疑 | 工程師會擔心匯流排增加延遲與抖動 | 硬即時留在單元內；ISR 只推事件；公開量測數據（第 11 節） |
| 中心瓶頸與單點故障 | 所有規則集中在中心 | 規則時間上限與 watchdog；多執行情境；安全動作不經中心 |
| 記憶體負擔 | 路由表、槽位、佇列、描述檔資訊都占空間 | 靜態配置、整數 ID、設計期資源估算；VM 為選配 |
| 抽象洩漏 | 有些硬體行為難以化成訊息（DMA、低功耗喚醒時序） | 允許單元內部用原生 C；匯流排只承諾語意層 |
| 學習曲線 | 單元、狀態與事件的區分需要教育 | IDE 預設正確語意；範本專案 |
| 和現有程式碼共存 | 客戶已有大量 C 程式碼 | 提供「包裝單元」，把既有模組包成單元；匯流排 API 可從手寫 C 直接呼叫 |
| 差異化被複製 | zbus 免費，ESPHome 開源 | 護城河在 IDE、描述檔生態、錄製重播與跨晶片工具，不在匯流排本身 |

## 11. 驗證計畫

### 最小原型

- **硬體**：一顆 STM32（例如現有的 STM32F746G-DISCO）或 ESP32-S3 觸控板。
- **單元**：觸控 GUI（LVGL）、實體按鈕（中斷）、Modbus RTU 感測器（可用 PC 端模擬從站）。
- **中心**：3 至 5 條規則，先編譯成 C。
- **錄製**：匯流排流量經 UART 或 RTT 送到 PC。

### 量測項目與目標（目標是假設，用來判斷成敗）

| 項目 | 量測方式 | 暫定目標 |
| --- | --- | --- |
| 按鈕中斷到畫面更新的延遲 | GPIO 打點加示波器或邏輯分析儀 | 中位數與最大值都在一個畫面更新週期內（約 16 至 33 ms） |
| 中斷到匯流排分派的延遲與抖動 | 時間戳 | 中位數低於 100 µs，最大值有界 |
| 匯流排本身的 RAM 與 Flash | linker map | RAM 數 KB、Flash 十數 KB 的量級 |
| 事件遺失 | 壓力測試：連續快速按鍵加高頻 Modbus | 零遺失，或溢出時有明確事件上報 |
| 錄製重播 | 錄下真機流量，在 PC 模擬器重播 | 重播後的 GUI 狀態與真機一致 |
| 換掉單元 | 把 Modbus 感測器換成模擬單元 | 規則不改一行 |

### 判斷

- 六項都過：進入產品化設計，先做 Zephyr 目標（以 zbus 為底）與 IDE 的單元庫、錄製重播。
- 延遲或記憶體不過：檢討訊息模型與中心的執行方式，不要硬上。

## 12. 未解問題

1. 匯流排自己實作，還是在 Zephyr 上直接用 zbus、在 FreeRTOS 與裸機上自己實作同一套 API？
2. 描述檔格式要自訂，還是貼近 Matter 的資料模型以利未來互通？
3. 規則 VM 要自製、選用現成（Lua、Berry、WebAssembly），還是延後？
4. 跨晶片協定要自訂，還是採用既有標準（例如 CBOR 加 COBS 封包、或 CAN 上的既有協定）？
5. 錄製重播在資源受限的晶片上要錄到什麼程度（全部、取樣、只錄事件）？
6. 這個架構對 EDT 模組業務（顯示模組即 GUI 單元）的價值，是否足以作為分拆談判中 EDT 的授權回用條件？
