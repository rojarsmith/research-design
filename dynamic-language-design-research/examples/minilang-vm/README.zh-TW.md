# minilang-vm：位元組碼編譯器與堆疊式 VM 範例

[回主報告](../../README.zh-TW.md)｜[路線圖](../../research/03-design-your-own-dynamic-language.zh-TW.md)｜[樹走訪版 minilang](../minilang/README.zh-TW.md)｜[階段 5：minilang-c](../minilang-c/README.zh-TW.md)｜[English README](README.md)

這是研究路線圖「階段 4」的可執行範例：替 [minilang](../minilang/README.zh-TW.md) 加上位元組碼編譯器與堆疊式 VM。詞法與語法分析器直接 `import minilang` 沿用，沒有複製也沒有修改；AST 之後的解析器、編譯器、程式碼物件、VM、反組譯器，以及位元組碼檔的寫出與讀入是新的，同樣寫成單一 Python 檔案，不依賴標準函式庫以外的套件。目的在示範階段 4 的元件與驗收方式，不是生產品質的 VM。已在 Python 3.14.6 執行並通過測試。

## 執行

```bash
cd dynamic-language-design-research/examples/minilang-vm
python3 -m unittest test_minilang_vm -v                        # 76 個測試
python3 minilang_vm.py ../minilang/programs/fib.ml             # 在 VM 上跑 minilang 的範例程式
python3 minilang_vm.py --dis ../minilang/programs/closures.ml  # 反組譯：指令、常數池、行號表、例外表
python3 minilang_vm.py --bench                                 # 三個基準各跑 5 次，約 2 至 3 分鐘
python3 minilang_vm.py --opt programs/bench_loop.ml            # 開啟編譯器最佳化
python3 minilang_vm.py --emit fib.mlc ../minilang/programs/fib.ml  # 不執行，改為寫出位元組碼檔
python3 minilang_vm.py fib.mlc                                 # 不經編譯，直接執行（或 --dis）位元組碼檔
python3 minilang_vm.py                                         # REPL，陳述以 ; 結尾，Ctrl-D 離開
```

76 個測試的組成：minilang 原有的 13 個測試在 VM 上以最佳化關閉與開啟各跑一次（26 個），4 個確認測試確實換成 VM 執行，46 個 VM 專屬測試。

## 管線

```text
原始碼 → minilang.tokenize() 與 Parser（沿用） → AST
      → Resolver：作用域、區域變數槽位、哪些變數被內層函式捕捉、upvalue 編號
      → Compiler：產生指令、跳躍回填
      → Code：常數池、行號表、例外表、迴圈表、計算出的最大堆疊深度
      → VM：單一分派迴圈；呼叫框架放在 VM 自己的串列，不遞迴宿主堆疊
      → 或 dump_program()：位元組碼檔（--emit），本 VM 與 ../minilang-c 的 C VM 都能載入
```

`--emit` 與檔案格式是為階段 5 加入的；格式（1.0 版）說明在 [minilang-c](../minilang-c/README.zh-TW.md#位元組碼檔格式-10) 與 `minilang_vm.py` 的 bytecode file 區段開頭。其他部分沒有改動：76 個測試相同，不改一行全部通過。

## 設計一覽

| 決策 | 本範例的選擇 | 對應路線圖的討論 |
| --- | --- | --- |
| 堆疊式或暫存器式 | 堆疊式；每個框架一個 Python 串列，前段是區域變數槽位，後段是運算元堆疊，長度 = 槽位數 + 最大堆疊深度 | 編譯簡單；配置方式同 CPython 框架的 localsplus |
| 編譯路徑 | AST 先經 Resolver 做名稱解析，再由 Compiler 產生指令，兩趟 | CPython 先建符號表再產生程式碼；Lua 單趟 |
| 指令編碼 | 固定寬度，每道指令兩個串列元素：opcode、運算元；跳躍目標與行號表都用位移 | 類似 CPython 的 16 位元 code unit |
| 分派 | `while` 迴圈裡的 `if/elif` 鏈，依基準中的出現頻率排序 | 相當於 Lua 的 while-switch；Python 沒有 computed goto |
| 常數池 | 字面值、全域名稱、巢狀函式的 Code 物件；以（型別, repr）去重，避免 `1`、`1.0`、`true` 在 Python 裡相等而被合併 | Lua 也把全域名稱放在常數表 |
| 行號表 | （起始位移, 行號）的連續段，行號改變才新增一段；出錯或呼叫內建函式時用二分搜尋查行號 | CPython 的 `co_linetable`、Lua 的 lineinfo |
| 最大堆疊深度 | 編譯後走過每條控制流程路徑計算，並檢查匯合點深度一致 | CPython 組譯階段的作法 |
| 例外 | 每個 Code 一張例外表（起點, 終點, 處理位移），內層在前；丟出時先查本框架，找不到就彈出框架，從呼叫端的 CALL 位移繼續找；沒有例外時不付成本 | CPython 3.11 起的零成本例外表 |
| 閉包 | 被內層函式用到的變數，在其作用域每次進入時建立新 cell；內層函式的 upvalue 指向 cell，跨多層時逐層轉手 | CPython 的 cell 設計。Lua 與 clox 讓變數留在堆疊當 open upvalue，作用域結束才搬到堆積；在 C 裡可省配置，在 Python 裡直接用 cell 較簡單也較快 |
| 呼叫框架 | VM 自管框架串列；深度上限沿用 minilang 的 400，超過是可被 `catch` 的 stack overflow | CPython 3.11 起 Python 對 Python 呼叫不遞迴 C 堆疊 |
| 與樹走訪共用的部分 | `VM` 繼承 `minilang.Interpreter`：內建函式、輸出注入、字串化與相等規則，以及運算子與索引的通用路徑（VM 只在快速路徑不適用時呼叫） | 兩個引擎共用值模型與錯誤訊息；名稱解析、控制流程、呼叫、閉包、例外由 VM 自己做 |

## minilang 的作用域與 VM 怎麼照做

minilang 的環境是執行 `let` 時才填入的字典，名稱指的是「查詢當下」最內層擁有它的環境。在同一個函式內這由原始碼順序決定，因為一個作用域的陳述只會依序各執行一次（迴圈本體每次迭代是新作用域），所以 Resolver 可以靜態決定槽位。閉包不同：它可能在外層之後的 `let` 執行前或執行後被呼叫。VM 照下表處理，每一項都有差異測試。

| 行為 | 樹走訪為何如此 | VM 的做法 |
| --- | --- | --- |
| 閉包看得到外層「之後才 `let`」的變數 | 呼叫時才沿環境鏈查名稱 | 這類名稱編成 `LOAD_CHAIN`/`STORE_CHAIN`：由內往外試這些 cell，跳過仍是 `UNDEFINED` 的，最後才是確定的綁定或全域表。只有「宣告在閉包建立之後」的名稱需要，其他都是槽位或 upvalue |
| 區域函式互相遞迴、`let f = fn() { ... f() ... }` | 同上 | 同上，自然成立 |
| 迴圈本體每次迭代是新作用域 | 每次執行區塊都建立 `Environment(env)` | 被捕捉的變數在區塊入口 `MAKE_CELL`，每次迭代一個新 cell |
| 函式內、不在迴圈裡的 `break` 會中斷呼叫端的迴圈 | `break` 是宿主例外 `BreakSignal`，會穿過函式呼叫與 `try` | 編成 `BREAK_OUT`：彈出框架，直到某個呼叫端的 CALL 位移落在迴圈表的範圍內，跳到該迴圈出口 |
| 頂層 `return`，以及找不到迴圈的 `break` | `ReturnSignal`、`BreakSignal` 從 `run()` 逸出成 Python 例外 | 丟出同一個 Python 例外 |
| `throw nil` 被 `catch` 成字串 `"nil"` | `RuntimeErr` 在值為 `None` 時改存訊息 | 用同一個 `RuntimeErr`，行為自然一致 |

這些行為多半是樹走訪實作方式的副作用，不是刻意的語言設計。VM 選擇照做以維持「同一套測試、結果一致」；要不要保留，應該在語意草案（階段 1）或規格（階段 8）裡決定。

## 驗證方式

1. **同一套測試。** `test_minilang.py` 被匯入後，以 `unittest.mock` 把 `minilang.Interpreter` 換成 VM 執行，沒有複製或改寫；最佳化關閉與開啟各跑一次。
2. **差異測試。** 同一段程式在樹走訪與 VM 上執行，比對印出的每一行與結束方式（回傳值、錯誤訊息全文含行號、或逸出的宿主例外）。涵蓋上表的作用域與控制流程、17 個程式（多數跨多行）的錯誤行號、11 個二元運算子對 15 種值的組合、一元與邏輯運算、索引與索引指派、內建函式，以及 `../minilang/programs/` 的範例程式。
3. **VM 內部。** opcode 表一致、常數池依型別去重、行號表是連續段且對應正確、最大堆疊深度、堆疊深度檢查會拒絕不一致的路徑、所有跳躍都已回填、if/else 與 break 的跳躍位置、例外表的巢狀順序、只有被捕捉的變數才變成 cell、upvalue 跨層轉手、反組譯輸出逐字比對、VM 呼叫不遞迴宿主堆疊。
4. **測試本身的檢查（一次性，未納入本目錄）。** 故意把 VM 改壞七處（閉包忽略外層之後的 `let`、區塊入口不建新 cell、`break` 不跨呼叫、二元運算回報錯誤行號、指派回報錯誤行號、深度上限差一、常數池只以值去重），每一處都讓測試失敗。另以隨機產生的程式（含閉包、遮蔽、迴圈、`try/catch`、`throw`、跨函式 `break`、頂層 `return`）比對兩種引擎與兩種最佳化模式，最終版本上 10,000 個程式全部一致。

## 效能量測

三個固定程式在 [programs/](programs/)：`bench_fib.ml`（遞迴費氏 fib(25)，242,785 次呼叫）、`bench_loop.ml`（函式內計數迴圈 100 萬次）、`bench_concat.ml`（2,000 個字串，各由 100 段 `str(i % 10) + ","` 拼成）。`--bench` 讓每個引擎交錯執行 5 次並取中位數，時間含解析與編譯（編譯每個程式約 80 微秒，可忽略），並檢查所有引擎輸出相同。

環境：Intel Core i7-11700（8 核）、64 GB 記憶體、Windows 11 Pro 10.0.26300、CPython 3.14.6 64 位元。2026-11-16 量測兩次，下表為第一次，括號內為 5 次的最小值至最大值，單位秒。

| 基準 | 樹走訪 | VM | VM `--opt` | VM 加速 | `--opt` 加速 |
| --- | --- | --- | --- | --- | --- |
| 遞迴費氏 | 1.240（1.144 至 1.289） | 0.470（0.418 至 0.538） | 0.461（0.423 至 0.518） | 2.64 倍 | 2.69 倍 |
| 計數迴圈 | 4.520（4.098 至 4.834） | 2.356（2.183 至 2.450） | 1.503（1.340 至 1.546） | 1.92 倍 | 3.01 倍 |
| 字串拼接 | 1.293（1.200 至 1.304） | 0.864（0.796 至 0.915） | 0.646（0.640 至 0.709） | 1.50 倍 | 2.00 倍 |

第二次量測的倍數：VM 2.80、1.90、1.45 倍；`--opt` 2.70、3.19、1.90 倍。兩次之間同一格的絕對時間最多差 21%，量測期間機器上可能有其他工作，所以請看倍數，不要看秒數。

**結論：在 Python 裡，VM 比樹走訪快，但只快 1.45 至 2.80 倍。** 原因用計數說明（以一次性的計數程式在較小輸入上量得，每單位的數字與輸入大小無關）：

| 基準與單位 | 樹走訪拜訪的節點 | VM 指令 | `--opt` 指令 | 樹走訪的 Python 函式呼叫 | 每節點耗時（推算） | 每指令耗時（推算） |
| --- | --- | --- | --- | --- | --- | --- |
| 費氏，每次呼叫 | 11.5 | 11.0 | 9.0 | 29.8 | 444 至 537 奈秒 | 176 至 200 奈秒 |
| 迴圈，每次迭代 | 14.0 | 17.0 | 11.0 | 33.1 | 323 至 333 奈秒 | 139 至 145 奈秒 |
| 拼接，每次內層迭代 | 20.2 | 23.3 | 17.2 | 48.3 | 320 至 325 奈秒 | 185 至 194 奈秒 |

- **VM 沒有少做步驟。** 它執行的指令數和樹走訪拜訪的節點數差不多，迴圈甚至更多。
- **省下的是宿主層的開銷。** 樹走訪每個節點至少一次 Python 函式呼叫（`exec`、`eval`、`binary`、`lookup`），每次 `return` 拋出並接住一個 Python 例外，每個區塊與呼叫建立一個字典環境，變數沿環境鏈查字典。VM 執行時幾乎不呼叫 Python 函式（費氏與迴圈每單位少於 0.5 次，含編譯；拼接是 3.9 次，因為 `str()` 本身是 Python 函式），變數是串列索引。
- **分派本身仍然很貴。** 每道指令 140 至 200 奈秒：一串 `op == 常數` 的比較、串列索引、型別檢查、裝箱的整數。CPython 的直譯器替 Python 原始碼做的事（逐指令分派、引用計數、物件配置），VM 的每道指令都還要再付一次，只是付得比樹走訪的每個節點少。

### 最佳化逐項量測

| 基準 | VM | 只開 `assign-statement` | 只開 `const-operand` | 只開 `compare-jump` | 全開（`--opt`） |
| --- | --- | --- | --- | --- | --- |
| 遞迴費氏 | 1.00 | 1.04、0.94 倍 | 0.96、0.87 倍 | 1.01、0.93 倍 | 1.02、0.97 倍 |
| 計數迴圈 | 1.00 | 1.64、1.62 倍 | 1.00、0.98 倍 | 1.02、1.01 倍 | 1.57、1.68 倍 |
| 字串拼接 | 1.00 | 1.22、1.30 倍 | 1.03、1.02 倍 | 1.08、1.03 倍 | 1.34、1.30 倍 |

每格是兩次量測相對於未最佳化 VM 的倍數。`bench_fib.ml` 沒有指派陳述，只開 `assign-statement` 時位元組碼完全相同，所以那一格的 0.94 至 1.04 倍就是雜訊範圍。

- **有效：`assign-statement`。** 陳述層級的 `x = e;` 直接存入，不產生 `DUP` 與 `POP`，迴圈每次迭代從 17 道指令降到 13 道，時間大致等比例下降。
- **在雜訊內：`const-operand`（`ADD_CONST`、`SUB_CONST`、`LT_CONST`）與 `compare-jump`（`JUMP_IF_NOT_LT`）。** 它們省下的是 `LOAD_CONST`，而 `LOAD_CONST` 在 if 鏈第 2 位，本來就便宜；新指令排在鏈的後段，要先經過十幾次比較。一次性實驗（未納入本目錄，5 次中位數）把這 4 個超指令移到鏈的最前面，結果未最佳化的 VM 變慢 33% 至 36%（費氏 0.644 秒變 0.856 秒、迴圈 2.71 秒變 3.67 秒），因為其他每道指令都多了 4 次比較，而最佳化版本也沒有變快。在 Python 的 if 鏈分派裡，指令集變大本身就有成本。這兩項保留在程式裡，讓量測可以重現。
- **沒有做：常數摺疊與全域快取。** 三個基準裡每個運算子都有變數運算元，沒有可摺疊的運算式；`LOAD_GLOBAL` 已經是一次字典查詢，在 Python 裡做 inline cache 需要的版本檢查成本相近。這兩點是推理，未量測。

### 對路線圖階段順序的意涵

- **「先樹走訪，再位元組碼」成立，而且主要理由不是效能。** 這個 VM 是對著一個會跑的參考實作與它的測試寫成的，差異測試與隨機程式比對才有仲裁依據，上面那些由實作決定的語意也是靠它發現的。
- **用 Python 做階段 4，驗證的是設計，不是速度。** Resolver、程式碼物件、閉包、例外表、堆疊深度計算都可以在這裡先做對、測完再移植；1.45 至 2.80 倍是 Python 宿主的性質，不能拿來預估 C 版本；C 版本的量測見 [minilang-c](../minilang-c/README.zh-TW.md#效能量測)。
- **量測要在目標宿主上做。** 在 Python 裡有效的最佳化（少發指令）與無效的最佳化（超指令）都和 if 鏈分派有關；C 的 `switch` 或 computed goto 分派成本結構不同，路線圖「效能演進的順序」的步驟 2（指令特化）要在 C 版本上另外量。

## 限制與未驗證

- 只在一台機器、一個 Python 版本（3.14.6）量測；倍數在兩次量測之間差最多 0.18，絕對時間最多差 21%。
- 樹走訪在宿主遞迴上限先到時回報的 `stack overflow (host recursion limit)`，VM 不會產生，因為 VM 不遞迴宿主堆疊；只在極深巢狀的運算式下才可能出現，未測試。
- 階段 4 的「位元組碼可快取、可離線預編譯」這個動機在 minilang-c 驗證：`--emit` 寫出檔案，C VM 執行結果相同。
- 這裡的記憶體由 Python 管理；階段 5 的回收器在 minilang-c。
- REPL 只手動以管線輸入驗證一次，輸出與 minilang 的 REPL 相同，沒有自動測試。
