# minilang-c：C 語言 VM 與標記清除垃圾回收器範例

[回主報告](../../README.zh-TW.md)｜[路線圖](../../research/03-design-your-own-dynamic-language.zh-TW.md)｜[階段 4：minilang-vm](../minilang-vm/README.zh-TW.md)｜[階段 2：minilang](../minilang/README.zh-TW.md)｜[English README](README.md)

這是研究路線圖「階段 5：記憶體管理」的可執行範例，同時補上階段 4 留下的 C 版量測。[minilang-vm](../minilang-vm/README.zh-TW.md) 的 Python 前端編譯程式並寫出位元組碼檔；`mlvm.c` 載入、驗證、執行這個檔案，並用精確的標記清除（mark-sweep）回收器管理記憶體。`mlvm.c` 是單一 C11 檔案，只依賴 C 標準函式庫；周邊工具只用 Python 標準函式庫。目的在示範階段 5 的元件與驗收方式，不是生產品質的 VM。

已在 Windows 11（WinLibs GCC 16.2.0、Python 3.14.6）與 Ubuntu 24.04 容器（podman；GCC 13.3.0、Python 3.12.3、AddressSanitizer 與 UndefinedBehaviorSanitizer）上執行並通過測試。

## 執行

```bash
cd dynamic-language-design-research/examples/minilang-c
gcc -std=c11 -Wall -Wextra -Werror -O2 -o mlvm mlvm.c -lm          # 唯一的建置步驟（Windows 上產生 mlvm.exe）
gcc -std=c11 -Wall -Wextra -Werror -O0 -o mlvm-O0 mlvm.c -lm       # 選用：--bench 的 -O0 欄位
python3 -m unittest test_minilang_c -v                             # 94 個測試，約 40 秒
python3 difftest.py                                                # 程式檔加 1,000 個隨機程式，6 種 VM 設定，約 1 分鐘
python3 minilang_c.py ../minilang/programs/closures.ml             # 用 Python 編譯、在 C VM 上執行
python3 ../minilang-vm/minilang_vm.py --emit fib.mlc ../minilang/programs/fib.ml
./mlvm fib.mlc                                                     # 不需 Python，直接執行位元組碼檔
./mlvm --stats --gc-stress fib.mlc                                 # 每次配置都回收；統計印到 stderr
./mlvm --dis fib.mlc                                               # 與 minilang_vm.py --dis 相同的反組譯
python3 minilang_c.py --bench                                      # 樹走訪、Python VM、C VM 各跑 5 次，約 2 分鐘
```

Windows 上 `python3` 可能要寫成 `python`。需要安裝的只有 GCC（WinLibs）與執行 minilang 用的 Python。

94 個測試的組成：minilang 原有的 13 個測試在 C VM 上執行（一般與開啟編譯器最佳化各一次；10 個語意測試另在 `--gc-stress` 下跑一次）、5 個確認測試真的換成 C VM、階段 4 的 24 個差異測試（每段程式在 4 種 C VM 設定上執行：一般、`--opt`、`--gc-stress`、兩者同時）、1 個執行所有程式檔的測試，以及 28 個檔案格式、載入器、數值與記憶體的測試。

## 管線

```text
原始碼 → minilang 語法分析器（階段 2）→ minilang_vm 的 Resolver 與 Compiler（階段 4）→ Code 物件
      → minilang_vm.dump_program()：位元組碼檔，格式 1.0          python3 minilang_vm.py --emit
      → 載入器：檔頭、每次讀取都檢查邊界、UTF-8 檢查、名稱 intern
      → 驗證器：運算元、跳躍目標、各表格、每條路徑的堆疊深度
      → 直譯器：單一 switch 迴圈；所有框架共用一個值堆疊
      → 堆積：所有物件串在一條串列上，只由標記清除回收器釋放              mlvm.c
```

## 為什麼前端留在 Python

| 做法 | 代價 | 決定 |
| --- | --- | --- |
| Python 前端，C 載入位元組碼檔 | 編譯需要 Python；語法錯誤由 Python 回報 | 採用 |
| 用 C 再寫一個前端 | 要在 C 重做階段 4 Resolver 的作用域規則（chain、cell、upvalue 逐層轉手），之後一次要測兩個編譯器加一個 VM | 不做 |

只有一個前端，就只有一套作用域決定，兩個引擎有差異時就是 VM 或 GC 的錯，不是兩個編譯器意見不同。這也驗證了階段 4 沒能驗證的動機：編譯結果可以快取、不帶編譯器執行，就像 Lua 允許只帶載入器的建置。代價是執行原始碼仍需要 Python；要做單一執行檔散布（階段 7）就需要 C 前端。

## 位元組碼檔格式 1.0

由 `minilang_vm.dump_program()`（`--emit`）寫出，由 `minilang_vm.load_program()` 與 `mlvm.c` 讀取。整數一律小端序。

```text
file   := "MLBC" major:u16 minor:u16 opcode_count:u16 flags:u16 code
code   := name:str nparams:u32 param:str*  nslots:u32 max_stack:u32
          ninstr:u32 (opcode:u8 operand:u32)*        -- 表格中的位移每道指令算 2，與 Code.code 相同
          nconsts:u32 const*
          nlines:u32 (offset:u32 line:u32)*           -- 行號表的連續段
          nhandlers:u32 (start:u32 end:u32 target:u32)*
          nloops:u32 (start:u32 end:u32)*
          nchains:u32 (name:str nmaybe:u32 upvalue:u32* kind:u8 final:u32)*
          nupvals:u32 (from_slot:u8 index:u32 name:str)*
          slot_name:str * nslots
const  := tag:u8，之後依序為 0 nil | 1 false | 2 true | 3 int:i64 | 4 超出 i64 的整數:str（十進位）
          | 5 float:f64 | 6 字串:str | 7 code（巢狀）
str    := nbytes:u32 UTF-8 位元組
```

- **版本。** 讀取端拒絕不同的主版本、較新的次版本、或 opcode 數量不同的檔案；重新編號 opcode 屬於主版本變更。`flags` 第 0 位元記錄編譯時是否開了最佳化，只供參考。
- **保留除錯名稱**（參數、槽位、upvalue），所以 `mlvm --dis` 印出的內容與 `minilang_vm.py --dis` 完全相同。這個相等是載入器最主要的測試：反組譯逐字相同，代表每個欄位都讀回來了。
- **載入器先驗證再執行。** 每次讀取都檢查邊界，每個數量都必須放得進剩下的位元組；字串必須是合法 UTF-8；運算元必須符合 opcode 的範圍（型別正確的常數、槽位、upvalue、chain、落在指令邊界的跳躍目標）；表格必須依序；再走過每條路徑計算堆疊深度，包含例外處理入口（深度 1）與迴圈出口（深度 0），拒絕堆疊下溢、匯合點深度不一致、執行到程式碼結尾之外、以及小於計算值的 `max_stack`。靜態無法檢查的「`LOAD_CELL` 執行時槽位裡確實是 cell」改在執行時檢查。

## 設計一覽

| 決策 | 本範例的選擇 | 對應路線圖的討論 |
| --- | --- | --- |
| 值的表示 | 16 位元組的標籤聯集：nil、bool、int64、double、內建函式直接存；其餘是指向堆積物件的指標 | 「標籤聯集；要決定 NaN-boxing 或 struct」：為了清楚選 struct |
| 堆積物件 | 字串、超出 64 位元的整數、串列、cell、閉包、程式碼物件；共用一個標頭：種類、標記位元、大小 | Lua 與 clox 也是這種物件串列 |
| 整數 | int64 快速路徑，溢位時改用任意精度（32 位元 limb）；放得回 int64 的結果一律存回 int64 | 樹走訪的整數就是 Python 的整數，不得不然 |
| 字串 | 不可變的 UTF-8，快取碼位數，因為 `len()` 與索引以碼位計 | 同上 |
| intern | 常數、全域名稱、內建函式名稱放進弱引用的 intern 表；執行時產生的字串不 intern | 全域表以指標比較鍵 |
| 閉包 | 階段 4 的位元組碼在作用域進入時把被捕捉的變數裝進 cell | 因此沒有 open upvalue，見「根集合」 |
| 呼叫框架 | 所有框架共用一個值堆疊；引數原地成為被呼叫者的前幾個槽位；最多 400 層 | 階段 4 的 VM 每次呼叫把引數複製到新串列 |
| 分派 | `for` 迴圈裡的 `switch` | computed goto 是 GCC 擴充，PEP 7 不允許；Lua 也為了可移植只用 switch |
| 錯誤 | C 函式回傳狀態並記錄錯誤；迴圈依例外表回溯 | 與 Python VM 相同的表格 |
| 平台 | 計時與二進位標準輸入輸出是僅有的平台相依程式碼，集中在一個區段 | 路線圖階段 7：平台相依收進一層 |

## 記憶體管理

### 為什麼選標記清除

| 方案 | 放在這裡代表什麼 | 採用者 |
| --- | --- | --- |
| 參考計數 | 每個會呼叫自己的閉包、每個包含自己的串列都會洩漏，因為它們都是循環（見下文）；必須再加一個循環回收器 | CPython（加循環 GC）、QuickJS（加循環移除） |
| 標記清除 | 能釋放循環；物件不移動，C 程式碼可以直接持有已在根集合中的物件指標；需要精確的根集合，回收時程式暫停 | Lua、clox（路線圖階段 5 的表） |
| 複製式或分代 | 停頓較短、沒有碎片，但物件會移動，C 程式碼持有的每個指標都必須是回收器能更新的 handle | V8（handle、`HandleScope`）、PyPy incminimark |

minilang 讓這個論點很具體：區域函式只要呼叫自己就一定是循環。在另一個函式裡寫 `fn countdown(k) { ... countdown(k - 1); }`，編譯結果是一個 cell 裝著這個閉包，而閉包的 upvalue 就是這個 cell。[`programs/gc_cycles.ml`](programs/gc_cycles.ml) 產生 20,000 個這種循環，外加 20,000 個包含自己的串列；回收器把它們都釋放了，測試檢查堆積始終低於 512 KB。只靠參考計數，這些一個也不會被釋放。CPython 為了同樣的原因另外維護循環回收器；PEP 703 則說明多執行緒共享物件時參考計數的成本。minilang 是單執行緒、沒有終結器，參考計數換來的「釋放時機確定」在這裡用不到。移動式回收器則需要整個 C 程式碼、以及之後階段 6 的 C API 都改用 V8 式的 handle。對這門語言而言，標記清除是正確前提下最小的設計：回收器本身約 160 行。

### 根集合

路線圖原本建議「VM 堆疊、全域表與開放 upvalue」。實際做出來，根集合必須是這樣：

| 根 | 原因 |
| --- | --- |
| 值堆疊到 `vm->sp` 為止 | 每個框架的槽位與運算元。迴圈把 `sp` 放在區域變數，在任何可能配置記憶體的動作之前發布（`SYNC()`）；回收器只標記 `stack[0 .. vm->sp)` |
| 每個框架的閉包與程式碼物件 | 腳本的程式碼物件只能從它的框架找到。框架的閉包同時也在堆疊上（就在引數下面），所以這個根目前是多餘的（拿掉它的植入錯誤沒有被發現，見下文）；保留是為了日後例如尾呼叫之類的改動不會把它弄壞 |
| 全域表的鍵與值 | 全域變數與內建函式 |
| 暫時根堆疊 | 在第一個物件可被找到之前就要再配置一次的 C 程式碼：串列與它的元素陣列、正在填寫程式碼物件的載入器、從文字解析的整數常數 |
| 正被丟出的值，或頂層 `return` 的值 | 從丟出到被 catch 之間 |
| 不是根：intern 表 | 弱引用：清除前先移除字串未被標記的項目 |
| 不是根：open upvalue | 根本沒有。階段 4 的位元組碼在作用域進入時把被捕捉的變數裝進 cell（CPython 的設計），所以每個被捕捉的變數每次進入作用域要配置一次，也沒有任何 upvalue 指向堆疊。Lua 與 clox 的 open upvalue 省下這次配置，但需要作用域結束時的「關閉」指令，而這份共用的位元組碼沒有 |

### 策略、統計與壓力模式

- **成長策略。** 堆積達到 `max(上次回收後存活量 x 2, 1 MiB)` 時回收；下限可用 `--gc-min` 調整（測試用 4 KiB 強迫頻繁回收）。倍數 2 與 clox 相同。
- **記帳。** 所有物件記憶體都經過同一個函式，所以 VM 隨時知道存活位元組數。表格、灰色堆疊、文字緩衝區與大整數的暫存空間用一般的 `malloc`，不計入。
- **標記**使用明確的灰色堆疊，所以巢狀 200,000 層的串列（有測試）不會讓 C 堆疊溢位。
- **統計**（`--stats`，或 serve 協定的 `stats`）：回收次數、總停頓與最長停頓、標記與清除各花的時間、配置與釋放的位元組數與物件數、存活位元組的峰值與目前值、下次門檻、載入與執行時間。
- **`--gc-stress`** 在每次配置時都回收，並把釋放的物件填成 `0xDB`，所以一個該是根卻沒列入的指標會立刻讀到垃圾，而不是偶爾才出錯。階段 4 的差異測試、階段 2 的語意測試、每個程式檔與每個隨機程式也都以這種模式執行。
- **拆除時**釋放所有物件，並檢查計數回到剛好 0；測試與隨機程式執行器遇到任何沒歸零的 session 都判定失敗。

### 驗收：路線圖對階段 5 的要求

| 路線圖的驗收標準 | 測試 | 結果 |
| --- | --- | --- |
| 長時間執行記憶體不增長 | [`programs/gc_churn.ml`](programs/gc_churn.ml) 每輪產生字串、串列、閉包與 cell，只保留 8 個結果；最小堆積 256 KiB 時，20,000 輪的峰值與 2,000 輪的峰值相差不到 25%，且低於 576 KiB | 通過 |
| 強制 GC 模式下測試全綠 | 階段 4 的差異測試、每個程式檔與每個隨機程式都在 `--gc-stress` 下執行，最佳化開與關各一次；階段 2 的語意測試也在此模式下執行 | 通過 |
| （新增）循環會被釋放 | `programs/gc_cycles.ml`：釋放超過 50,000 個物件，峰值低於 512 KB | 通過 |
| （新增）沒有東西逃出記帳 | 每個 VM session 結束時計數為 0；LeakSanitizer 沒有發現洩漏 | 通過 |

### 壓力模式找得到漏掉的根嗎

一次性檢查，未納入本目錄：在 `mlvm.c` 的副本裡一次植入一個根集合錯誤，共七個；每個副本以預設堆積、4 KiB 堆積與 `--gc-stress` 執行 158 個程式（8 個程式檔加 150 個隨機程式），並在 AddressSanitizer 下跑測試套件。

| 植入的錯誤 | 結果不同的程式數，Windows：預設堆積／4 KiB／`--gc-stress` | ASan：失敗的測試數 | ASan：`--gc-stress` 下結果不同的程式數 |
| --- | --- | --- | --- |
| 1. 通用運算子路徑之前沒有 `SYNC()` | 0／0／31 | 0 | 32 |
| 2. `MAKE_CELL` 之前沒有 `SYNC()` | 0／0／0 | 2（為這個錯誤補寫的測試） | 0 |
| 3. 新串列在兩次配置之間沒有列入根 | 0／0／122 | 25 | 124 |
| 4. 載入器沒有把正在填寫的程式碼物件列入根 | 0／134／158 | 50 | 158 |
| 5. 不標記框架的閉包 | 0／0／0 | 0 | 0 |
| 6. 不追蹤程式碼物件的常數 | 3／121／158 | 52 | 158 |
| 7. intern 表不是弱引用 | 0／0／0 | 6 | 130 |

- **用預設堆積時，漏根的錯誤幾乎看不見**：這些程式很少達到 1 MiB 門檻，只有一個錯誤在 158 個程式中的 3 個出現。讓它們現形的是壓力模式。
- **沒有任何一種方法單獨抓到全部六個真的錯誤。** 壓力模式下的隨機程式抓到 1、3、4、6；ASan 下的測試套件抓到 2（只因為隨機程式漏掉它之後補寫了一個測試）、3、4、6、7。錯誤 7 讓死字串留在 intern 表裡，它們只會被讀取、不會被印出，所以只有 ASan 看得出。錯誤 1 躲過了測試套件，被隨機程式抓到。
- **錯誤 5 其實不是錯誤。** 執行中函式的閉包同時也在堆疊上（就在引數下面），本來就找得到；明確列入根是為了防止日後的改動弄壞它。

## 與樹走訪一致：Python 執行環境放進 minilang 的東西

階段 4 的 VM 能和樹走訪共用運算子，是因為兩者都跑在 Python 上。C VM 不行；要讓輸出完全相同，就得把 minilang 從未規定、卻從 Python 繼承來的行為一條條寫下來。`mlvm.c` 大約有 700 行只為了這件事。

| 行為 | 來源 | C VM 的做法 |
| --- | --- | --- |
| 整數沒有大小上限；`9223372036854775807 + 1` 是精確值 | Python 的 `int` | 有溢位檢查的 int64，溢位後改用任意精度整數，除法用 Knuth 演算法 |
| `int / int` 整除時是整數，否則是正確捨入的浮點數，連極大整數也一樣 | `Interpreter.binary()` 加上 Python 的真除法 | 移植 CPython `long_true_divide` 的捨入 |
| 整數與浮點數精確比較（`2**53 + 1 != 2.0**53`） | Python 的混合比較 | 透過 double 的整數值做精確比較 |
| `%` 的結果與除數同號，整數與浮點數皆然 | Python | 同樣規則，含 CPython 的 `float_rem` |
| 浮點數以 `repr()` 印出，整數值的浮點數印成整數（`1e22` 印出 23 位數） | `stringify()` | 最短可讀回的位數；整數值的 double 印出精確整數 |
| `num()` 接受 `" 7 "`、`"1_000"`、`"inf"`、`"-Infinity"`、`"nan"`，拒絕 `"--5"` | `int()` 與 `float()` 的文法、Unicode 空白 | 相同文法；只接受 ASCII 數字（見限制） |
| `num()` 的錯誤訊息用 Python 的 `repr()`：`'abc'`、`"it's"`、`[1, [...]]` | 訊息裡的 `"%r"` | Python 的引號與逸出規則，包含自己的串列印成 `[...]` |
| `len()` 與索引以碼位計 | Python 的 `str` | UTF-8 加快取的碼位數 |
| 極大整數與浮點數混合運算是 `OverflowError`，不是 minilang 錯誤，`try` 接不到 | Python 的型別轉換 | 回報為 Python 層錯誤，型別與訊息相同 |
| 印出超過 4,300 位數的整數是 `ValueError` | `sys.get_int_max_str_digits()` | 相同上限 |
| 包含自己的串列無法印出（`RecursionError`）；在函式內會在呼叫處變成 `stack overflow (host recursion limit)` | Python 遞迴上限加上 `Interpreter.call()` | 巢狀上限 1,000 層，同樣方式轉換 |
| `throw v` 的訊息在丟出時就計算，所以無法印出的值即使會被 `catch` 接住也會失敗 | `RuntimeErr(stringify(value), ...)` | 相同順序 |

這些應該寫進語意草案（階段 1）或規格（階段 8）：要嘛 minilang 自己規定數值與文字格式，要嘛每個實作都得重現某個特定宿主。

## 驗證方式

1. **同一套測試，不改一行。** `test_minilang.py`（階段 2）與 `test_minilang_vm.py` 的差異測試（階段 4）被匯入後，以 `unittest.mock` 換成 C VM 執行：階段 2 換 `minilang.Interpreter`，階段 4 換 `VM_ENGINES`。`minilang_c.py` 的 `CVM` 與樹走訪有相同的建構子與 `run()` 介面；它在 Python 編譯，再交給常駐的 `mlvm --serve` 程序執行，每個 `CVM` 是一個獨立的 VM session，有自己的堆積與全域表。
2. **差異測試**（`difftest.py`）。每個程式檔與一批隨機產生的程式，在樹走訪與 6 種 C VM 設定（一般與 `--opt` 位元組碼，各配預設堆積、4 KiB 堆積、`--gc-stress`）上執行；印出的每一行與結束方式必須完全相同，Python 層錯誤也算在內。
3. **檔案格式與載入器。** Python 端逐位元組來回一致；每個程式的 C 反組譯與 Python 完全相同；檔案在任何位置截斷都被拒絕；5 種損壞的檔頭與 21 種損壞的程式碼物件都被拒絕，各有明確訊息。
4. **數值。** 30,000 個 double（隨機位元、2 的冪次、邊界值）的 `repr()` 與 `str()` 與 Python 比對；150 組隨機大整數經過 8 種運算子；9 個運算子作用在 14 種數值的每一對上；`num()` 作用在 44 個字串與 9 個其他值上。
5. **記憶體。** 上述驗收測試、成長策略、壓力模式、深層結構，以及每個 session 都釋放所有位元組。
6. **Sanitizer。** WinLibs 在 Windows 上沒有 AddressSanitizer 與 UBSan 的執行期函式庫（`cannot find -lasan`、`-lubsan`）。Windows 上另以不需執行期函式庫的 `-fsanitize=undefined,float-cast-overflow -fsanitize-trap=all` 建置，測試全部通過。Ubuntu 24.04 容器中以 `-fsanitize=address,undefined,float-cast-overflow -fno-sanitize-recover=all` 建置，測試套件與另外 2,000 個隨機程式（各 6 種設定）全部通過，沒有任何 sanitizer 報告，LeakSanitizer 也沒有。

完整執行 `python3 difftest.py --count 10000 --seed 1`（最終版 `mlvm.c`，Windows 上 599 秒）：10,008 個程式（8 個程式檔加 10,000 個產生的程式）、60,048 次 C VM 執行，0 個差異，也沒有任何 session 留下位元組。樹走訪的結束方式：4,601 個以值結束、5,105 個以未捕捉的執行期錯誤結束（所以比對了錯誤文字與行號）、139 個頂層 `return` 逸出、112 個 `break` 逸出、51 個 `RecursionError`；共比對 222,164 行輸出。回收器在每個 `--gc-stress` 設定下執行 2,337,959 次，4 KiB 堆積約 51,000 次，預設堆積 77 次。產生器較早的版本找到一個真的差異，在 serve 協定而不在 VM：無法印出的結尾值（包含自己的串列）會產生格式錯誤的結束行。已修正，並由這批程式涵蓋。

## 效能量測

三個程式沿用階段 4 的 [../minilang-vm/programs](../minilang-vm/programs/)：遞迴費氏 fib(25)（242,785 次呼叫）、一百萬次的計數迴圈、2,000 個各由 100 段拼成的字串。`python3 minilang_c.py --bench` 讓每個引擎交錯執行 5 次，並檢查所有引擎輸出相同（另含一次 `--gc-stress` 執行）。Python 引擎在同一程序內計時，含解析與編譯，與階段 4 相同。C VM 的時間是 `--stats` 回報的執行時間；載入檔案約 7 微秒，不計入，編譯則事先以 `--emit` 完成。

環境：Intel Core i7-11700（8 核）、64 GB 記憶體、Windows 11 Pro 10.0.26300、CPython 3.14.6、WinLibs GCC 16.2.0（UCRT）。2026-11-16 以最終版 `mlvm.c` 量測兩次，下表為第二次，單位秒，5 次的中位數，括號內為最小值至最大值。量測時機器上同時有數個虛擬機器與其他工作在跑：Python 引擎的中位數比各自的最小值與階段 4 對同一程式的數字高出最多 60%，而 C VM 的時間在兩次量測與先前一次試跑之間差異不到 10%。

| 基準 | 樹走訪 | Python VM | C VM -O2 | C VM -O2，`--opt` 位元組碼 | C VM -O0 |
| --- | --- | --- | --- | --- | --- |
| 遞迴費氏 | 1.670（1.130 至 1.803） | 0.724（0.433 至 0.767） | 0.0058（0.0051 至 0.0088） | 0.0061（0.0057 至 0.0063） | 0.0326（0.0325 至 0.0367） |
| 計數迴圈 | 6.587（6.233 至 6.871） | 3.352（3.162 至 3.589） | 0.0218（0.0212 至 0.0246） | 0.0184（0.0181 至 0.0222） | 0.1831（0.1657 至 0.1917） |
| 字串拼接 | 2.024（1.904 至 2.087） | 1.317（1.268 至 1.394） | 0.1067（0.0994 至 0.1274） | 0.1053（0.0976 至 0.1149） | 0.1740（0.1692 至 0.1790） |

C VM（-O2、一般位元組碼）相對 Python 引擎的加速倍數，因為 Python 的計時有雜訊，列三種算法：

| 基準 | 相對樹走訪，第一次／第二次 | 相對 Python VM，第一次／第二次 | 相對階段 4 的中位數（樹走訪／Python VM） |
| --- | --- | --- | --- |
| 遞迴費氏 | 286／288 倍 | 123／125 倍 | 214／81 倍 |
| 計數迴圈 | 312／302 倍 | 148／154 倍 | 207／108 倍 |
| 字串拼接 | 18／19 倍 | 12／12 倍 | 12／8 倍 |

最後一欄以階段 4 的中位數（同一台機器、較安靜的一天量得：1.240、4.520、1.293 秒與 0.470、2.356、0.864 秒）除以本次 C 的中位數，是最保守的數字。

在 Windows 上，啟動程序、載入與結束約多 20 毫秒：整個程序的中位數是費氏 0.026 秒、迴圈 0.042 秒、拼接 0.126 至 0.131 秒。

**結論：呼叫與迴圈上，C VM 比兩個 Python 引擎都快兩個數量級（同一份位元組碼，比 Python VM 快 81 至 154 倍）；配置密集的程式快一個數量級（8 至 19 倍），而且其中約 30% 的時間在回收器。** 以階段 4 量到的指令數推算（推算值，非直接量測），C VM 每道指令在費氏約 2.2 奈秒（每次呼叫 11 道）、迴圈約 1.3 奈秒（每次迭代 17 道）、拼接約 23 奈秒（每次內層迭代 23.3 道，大部分花在配置與複製字串），Python VM 則是 140 至 200 奈秒。

### 回收器的成本

| 基準 | 配置量 | 物件數 | 回收次數 | 總停頓（標記、清除） | 最長停頓 | 佔執行時間 | `--gc-stress`：回收次數、執行時間 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 遞迴費氏 | 載入時 1.4 KB | 14 | 0 | 0 | 0 | 0% | 22、0.005 秒 |
| 計數迴圈 | 載入時 1.6 KB | 16 | 0 | 0 | 0 | 0% | 25、0.022 秒 |
| 字串拼接 | 69.8 MB | 600,021 | 66 | 29.0 毫秒（0.024、28.9）與 36.6 毫秒（0.031、36.6） | 0.85 與 1.01 毫秒 | 29% 與 30% | 600,030、0.17 秒 |

- **費氏與迴圈執行時完全不配置**：整數是直接值，也沒有被捕捉的變數，所以回收器從未執行。
- **拼接有 30% 的時間在回收器，而且幾乎全是清除階段。** 兩次回收之間累積約 1 MiB 的死字串（最小堆積）；標記只找到少數存活物件（66 次回收合計 0.03 毫秒），清除則每次走過並釋放約 9,000 個死字串（每個 48 至 61 奈秒）。標記清除的成本隨堆積大小成長，而不是隨存活資料成長。複製式或分代的新生代在這裡只會碰到存活物件，依大小分級的配置器則能讓配置與釋放都更便宜；這是推理，不是量測。對這種工作負載，下一步該改的是配置器，不是標記階段。
- **停頓維持在一毫秒左右**，因為堆積很小：最長 1.01 毫秒。
- **存活物件少時，壓力模式很便宜。** 每次配置都回收讓拼接回收了 600,030 次，只慢約 1.6 倍，因為每次回收只標記存活集合、清除一兩個物件。整個測試套件與隨機程式都在壓力模式下跑，成本也因此不高。

### 階段 4 的最佳化在 C VM 上

相對一般位元組碼的倍數，兩次量測：

| 基準 | 只開 `assign-statement` | 只開 `const-operand` | 只開 `compare-jump` | 全開（`--opt`） |
| --- | --- | --- | --- | --- |
| 遞迴費氏 | 1.02、1.01 倍 | 1.08、1.14 倍 | 0.96、0.94 倍 | 0.98、0.96 倍 |
| 計數迴圈 | 1.27、1.16 倍 | 1.03、1.02 倍 | 0.95、0.99 倍 | 1.16、1.18 倍 |
| 字串拼接 | 1.07、1.06 倍 | 1.10、1.01 倍 | 1.09、0.97 倍 | 1.03、1.01 倍 |

`bench_fib.ml` 沒有指派陳述，只開 `assign-statement` 時位元組碼與一般相同，那一格就是雜訊範圍：約 2%。

- **少發指令仍然有效，但不如在 Python 明顯。** `assign-statement` 讓迴圈每次迭代從 17 道指令降到 13 道，快 1.16 至 1.27 倍（Python VM 是 1.62 至 1.64 倍）。常數運算元超指令讓費氏最多快 14%。
- **比較加跳躍的超指令在 C 上一樣無效**（費氏與迴圈 0.94 至 0.99 倍）。三項全開時，費氏比一般慢 2% 至 4%。在兩種宿主上，量測到有效的都是「減少指令」的改動，不是「合併指令」的改動。
- **C 編譯器的最佳化比這些都重要**：-O2 比 -O0 在費氏快 5.6 倍、迴圈 8.2 至 8.4 倍、拼接 1.6 倍；拼接的工作主要在 C 函式庫的配置器裡，兩種最佳化等級都一樣。

### 對路線圖的意涵

- **階段 4 的提醒成立**：Python 原型的 1.45 至 2.80 倍無法預估 C VM；C VM 執行同一份位元組碼，在呼叫與迴圈上比 Python VM 快 81 至 154 倍。
- **配置密集的情況由記憶體管理決定。** 移到 C 之後，字串拼接剩下的成本是配置與清除，不是分派，所以在配置變便宜之前，路線圖「效能演進的順序」（指令特化、再 JIT）對這類工作負載用不上。

## 限制與未驗證

- 只在一台機器上量測，只用 GCC 建置（Windows 上 WinLibs 16.2.0、容器內 13.3.0）；沒有試 Clang 與 MSVC。
- 執行原始碼需要 Python，因為前端是 Python 的；沒有 C 版 REPL。
- `num()` 只認 ASCII 數字。Python 的 `int()` 與 `float()` 也接受其他 Unicode 十進位數字（阿拉伯-印度數字、全形數字），所以對這類文字的 `num()` 結果不同。
- `num()` 的錯誤訊息中，Python 依 Unicode 資料庫決定哪些非 ASCII 字元要逸出；C VM 用固定清單（控制字元、空白、格式字元、代理字元、私用區），所以未指派或罕見的碼位可能逸出方式不同。
- 印出巢狀串列到 1,000 層就停止並回報 `RecursionError`。樹走訪的上限來自 Python 的堆疊，且取決於堆疊上已用的深度，所以巢狀略多於 1,000 層時兩個引擎可能結果不同；樹走訪確切停在幾層沒有量測。測試只涵蓋循環（兩邊都失敗）與 200,000 層（兩邊都失敗）。
- 與階段 4 相同，樹走訪在極深巢狀的「運算式」上回報的 `stack overflow (host recursion limit)` 不會出現在 VM。
- 載入器在測試中拒絕了每一個截斷與損壞的檔案，在 sanitizer 下也沒有報告，但沒有用隨機位元組做模糊測試，所以對任意輸入的記憶體安全並未證明。
- 回收器在整個回收期間暫停程式；沒有實作增量式或分代回收。堆積統計只計物件記憶體，不含值堆疊、表格與 `malloc` 的額外開銷，也沒有量測行程記憶體（RSS）。
- 隨機程式的數字與字串取自固定清單，多半是 ASCII。會印出時間（`clock()`）的程式在比對時把 `clock()` 換成 `0`。
- 植入錯誤的檢查是一次性的；那七份 `mlvm.c` 副本不在本目錄。

## 若要往下推進

1. 階段 6：所有狀態已經在 `VM` 結構裡（serve 模式在一個程序裡同時跑多個 VM）；可以在上面加一層用不透明 handle 與狀態碼的 C API，並把 C 呼叫端持有的 handle 加進根集合。
2. 階段 7：寫一個 C 前端，讓單一執行檔就能跑原始碼；再為這裡測過的兩個平台建 CI。
3. 只有在停頓時間開始變得重要時，才去量測增量式回收器（Lua 5.1 的做法，需要寫屏障）；在這裡量到的規模下並不重要。
