# Dynamic Languages from Zero: How Python and Node.js Came to Be, How to Evaluate Portability, and How to Design Your Own

Research date: 2026-10-19. This is an English overview; the full research is in Traditional Chinese. It answers three questions for engineers: how dynamic languages such as Python and Node.js went from nothing to a working ecosystem, how to evaluate a language's portability and execution environment, and how to design a dynamic language from scratch. Historical and technical facts cite official documentation or the authors' own papers and posts; the evaluation tables, staged plan, and example are this study's proposals, not any community's standard.

One-line conclusion: a dynamic language does not start as a "language" with a "platform"; it starts as a small interpreter written in C to solve a concrete problem, leaning on an existing operating system and C compiler, and then grows an ecosystem through extensibility, a specification process, and a platform support policy. Designing your own follows the same order: a working tree-walking interpreter first, then bytecode, garbage collection, JIT, and multi-platform support only when needed.

Portability is evaluated in six layers: support policy, implementation language and toolchain, system dependency layer, extension ABI, binary distribution, and constrained environments; plus three runtime dimensions: performance tier, memory model, and concurrency model.

The design roadmap has nine stages: problem and scope, syntax and semantics draft, tree-walking interpreter, standard library and modules, bytecode compiler and VM, memory management, host interoperability, platforms and distribution, specification and process; runnable examples carry out stages 2, 4, 5, 6 and 8. Key decisions (value model, scoping, error model, concurrency, embedded versus standalone) are made in the first two stages because they are hard to change later.

The minilang-vm example carries out stage 4's acceptance test. On Python 3.14.6 the VM ran 1.45x to 2.80x faster than the tree-walker on three fixed benchmarks over two measurement runs, and up to 3.19x with compiler optimizations; nearly all of that extra gain came from one change, storing assignment statements without a DUP/POP pair. The speedup comes from removing host-level work: the tree-walker makes Python function calls for every AST node and passes `return` as an exception. Dispatch itself is not cheaper, since each VM instruction still costs roughly 140 to 200 ns in Python (derived from measured counts and times). A Python prototype therefore validates the compiler design, not the performance a C VM would reach.

The minilang-c example carries out stage 5's acceptance test and gives the missing C numbers. A C11 VM with a precise mark-sweep garbage collector loads minilang-vm's bytecode files; the stage 2 and stage 4 test suites pass on it unchanged, and 10,000 random programs match the tree-walker in all 60,048 runs across six configurations, including collecting on every allocation, with no AddressSanitizer or UBSan report. On the same machine it runs the same bytecode 81x to 154x faster than the Python VM on calls and loops and 8x to 12x faster on string building, where about 30% of the time is the collector, nearly all of it sweeping. In minilang every local function that calls itself is a reference cycle, which is the concrete case against reference counting alone. Matching the tree-walker also meant reproducing Python's integers, float formatting and `int()`/`float()` parsing, none of which minilang had specified.

The minilang-embed example carries out stage 6's acceptance test without forking the VM: `minilang.c` includes stage 5's `mlvm.c`, whose command-line build, output and tests stay unchanged. A C host holds minilang values only through handles in scopes, which are the collector's roots, and a generation count turns a stale handle into an immediate error; errors cross the boundary as status codes, without `longjmp`, and minilang and C can call each other reentrantly. The C tests' 2,526 checks pass plain, collecting on every allocation and with a 4 KiB heap, and with AddressSanitizer, UBSan and LeakSanitizer on Linux. Of five bugs planted one at a time, stress mode caught four; the fifth, a stale pointer into a value stack that had moved, only AddressSanitizer saw. Crossing the boundary costs about two to five minilang calls. Embedding also meant that no file may kill the process, so the example fixes two ways one could, including the 64-level nesting crash that stage 8's tests found.

The minilang-spec example carries out stage 8. A reference manual in English and Traditional Chinese describes minilang 1.0 rather than an engine: 50 implementation-defined or surprising behaviours of the engines, including those stages 4 and 5 had to copy, are each specified, made implementation-defined, or kept as legacy behind one of nine proposed changes, and Core and Full conformance levels set what a new implementation must match. 201 Test262-style conformance tests, a standard-library runner and a release gate check the three engines; after stage 6's fix all three pass 201 of 201 in all six configurations, through their Python APIs and their command lines, with no drift from their documented implementation-defined behaviour, so the gate is met. The suite found the C VM's nesting crash and a disagreement over printing, inside a function, a list that contains itself; writing the manual found that integer division rounds whole quotients through a float (`9007199254740993 / 1` is `9007199254740992`), which the existing differential tests could not catch because all three engines do it. The three engines are not three independent implementations, since the lexer and parser exist once, and stage 8's own acceptance test, an implementation written from the manual alone, has not been done.

## Boundaries

Platform tiers, toolchain versions, and release schedules are snapshots as of the research date and change between versions; recheck before implementation. Performance figures for Python, Node.js, V8 and Lua are each project's own benchmark reports and were not re-measured; the minilang-vm and minilang-c figures, minilang-embed's boundary-crossing cost and minilang-spec's conformance results were measured on one machine, as described in their READMEs. Stage sizes are estimates derived from public teaching material and reference implementations; only the minilang, minilang-vm, minilang-c, minilang-embed and minilang-spec examples were executed and tested.
