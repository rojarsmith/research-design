# 04 如何融會貫通：語言、編譯器與處理器的契約堆疊

研究日期：2026-10-19。前三篇分別回答三個問題，本文把它們放回同一張圖，並給出一條可以自己動手驗證的學習路線。核心主張：**C、編譯器、ABI、指令集、微架構是一疊互相承諾的契約；懂了每一層承諾什麼、不承諾什麼，三個問題就變成同一個問題。**

## 契約堆疊

```
┌──────────────────────────────────────────────────────────────┐
│ C 標準（ISO/IEC 9899）                                       │
│   承諾：抽象機器的可觀察行為；未定義／實作定義行為的清單     │
│   不承諾：int 幾位元、位元組序、函式呼叫怎麼傳參、執行速度   │
├──────────────────────────────────────────────────────────────┤
│ 實作（編譯器 + 函式庫）                                      │
│   承諾：把合法程式翻成等價的目標程式；把實作定義行為寫成文件 │
│   不承諾：對未定義行為的程式做任何特定的事                   │
├──────────────────────────────────────────────────────────────┤
│ ABI（psABI、AAPCS、SysV）                                    │
│   承諾：資料模型、對齊、參數與回傳值暫存器、堆疊框架、重定位 │
│   不承諾：指令怎麼執行                                       │
├──────────────────────────────────────────────────────────────┤
│ 指令集架構（ISA：RV32IM、ARMv7-M、x86-64）                   │
│   承諾：每條指令對架構狀態（暫存器、記憶體、PC）的效果       │
│   不承諾：花幾個週期、有沒有快取、是否亂序                   │
├──────────────────────────────────────────────────────────────┤
│ 微架構與實體晶片                                             │
│   承諾：以某個速度與功耗正確實作 ISA                         │
│   不承諾：任何上面幾層的語意                                 │
└──────────────────────────────────────────────────────────────┘
```

讀法：

- 「C 是怎麼被創造的」是第一層的歷史：Ritchie 把 PDP-11 的能力抽象成一台機器，後來的標準把這台機器寫成條文。
- 「編譯器是怎麼被創造的」是第二層與第三層：把抽象機器的語意翻到某個 ISA，並遵守一份 ABI；自舉與交叉編譯解決第一個編譯器從哪裡來。
- 「評估處理器能否跑 C」是從第四層往上看：這個 ISA 離 C 抽象機器有多遠、有沒有人幫它做好第二、三層。

一旦接受這張圖，三個問題的答案就互相解釋：C 之所以長成這樣，是因為它要能被便宜地翻到當年的 ISA；編譯器之所以能移植，是因為語言層與 ISA 層之間有 ABI 這條明確邊界；處理器之所以能或不能跑 C，是看它能否以可接受的代價提供這台抽象機器。

## 同一個程式穿過堆疊的樣子

以 `fib` 為例，[tinyc 實作](../labs/tinyc/README.md) 可以印出每一層：

| 層 | 指令 | 看到什麼 |
| --- | --- | --- |
| 原始碼 | `cat examples/01_fib.c` | 抽象機器上的運算 |
| token | `python3 tinyc.py examples/01_fib.c --tokens` | 詞法分析結果 |
| AST | `python3 tinyc.py examples/01_fib.c --ast` | 語法結構，`a[i]` 已變成 `*(a + i)` |
| RV32 組合語言（笨版） | `python3 tinyc.py examples/01_fib.c` | 每個運算都經過堆疊的直譯式生碼 |
| RV32 組合語言（工業級） | `clang --target=riscv32 -march=rv32im -mabi=ilp32 -O2 -S examples/01_fib.c` | 相同 ABI 下，最佳化後的暫存器使用 |
| x86-64 組合語言（tinyc） | `python3 tinyc.py examples/01_fib.c --target x86_64` | 同一棵語法樹、同一個生碼策略，換一個 `Machine` 後端 |
| x86-64 組合語言（工業級） | `gcc -O2 -S examples/01_fib.c` | 不同 ISA 與 ABI 下、最佳化後的同一個程式 |
| 原生執行 tinyc 的輸出 | `cc fib_x86.s runtime.c -o fib_x86 && ./fib_x86` | 玩具編譯器的程式碼在真實處理器、真實 ABI、真實 libc 旁執行 |
| 機器碼 | `clang --target=riscv32 -march=rv32im -c out.s && llvm-objdump -d out.o` | 組譯器把文字變成位元 |
| 執行 | `python3 rv32sim.py out.s --stats` | ISA 層的語意：指令數、堆疊深度、結束碼 |
| 差分驗證 | `python3 run_tests.py` | 四條路徑（tinyc→RV32 模擬器、主機 gcc、tinyc→x86-64 原生、clang→RV32 模擬器）輸出一致 |

`run_tests.py` 的結果是本主題最重要的一個觀察：同一份 C 原始碼經過三種完全不同的編譯器與兩種處理器、四種組合，輸出與結束碼完全相同。這就是 C 標準這份契約的可觀察內容。

## 學習路線：以可驗證的里程碑推進

每一關都有「做出來」與「說得出來」兩個驗收條件。建議順序不要調換，因為後面的每一關都依賴前一關建立的詞彙。

### 第 1 關：讀懂一段 `-O0` 組合語言（1 至 2 天）

- 做：把 `01_fib.c` 用 tinyc 與 `gcc -O0 -S` 各編一次，逐行對照 prologue、參數存放、遞迴呼叫、回傳。
- 說：為什麼 `main` 不是第一條指令；`ra`／回傳位址存在哪裡；區域變數為什麼在 `fp` 的負偏移。

### 第 2 關：改 tinyc，加一個語言功能（2 至 4 天）

- 做：加入 `char` 型別與 `lb`／`sb` 指令，或加入 `while` 內的 `break`。改完後 `run_tests.py` 必須仍全綠，並新增一個範例。
- 說：這個功能在詞法、語法、語意、生碼各階段分別需要改什麼。

### 第 3 關：並排讀兩個後端，親手弄壞 ABI（2 天）

- 做：讀 `tinyc.py` 中的 `RV32` 與 `X86_64` 類別，自己整理一張差異表後再對照 [tinyc README](../labs/tinyc/README.md) 的表。接著拿掉 `aligned_call` 的補齊，跑 `run_tests.py`，觀察 `--check-align` 的路徑 A 失敗，以及路徑 D 是否在 `printf` 內當掉。
- 說：兩個後端之間哪些程式碼可以共用、哪些不能；ABI 為什麼要規定對齊；為什麼同樣的錯在模擬器上無感、在真實 libc 旁邊會當。

### 第 4 關：換一顆「更弱的處理器」（3 至 5 天）

- 做：為 tinyc 加第三個後端 RV32I（無 M 擴充），把乘除改成呼叫 `__mulsi3`、`__divsi3`、`__modsi3`，在 `runtime_rv32.s` 用移位與加法實作，再比較指令數。有 QEMU 時可改做 ARMv7-M。
- 說：這就是 [03](03-processor-c-readiness.zh-TW.md) 中「可以但有代價」的具體樣貌；代價來自哪些指令。

### 第 5 關：用真實工具鏈評估一顆真實處理器（1 至 2 天）

- 做：選一顆手上的 MCU 或 QEMU 支援的核心，走完 [03](03-processor-c-readiness.zh-TW.md) 的五步流程，填寫 [評估清單](../labs/probe/checklist.zh-TW.md)。
- 說：給出「可以／可以但有代價／不可以」的結論與證據。

### 第 6 關：閱讀一個真實編譯器的後端（持續）

- 做：讀 chibicc 全部的 commit 歷史，再讀 GCC `gcc/config/riscv/riscv.md` 或 LLVM `llvm/lib/Target/RISCV/` 的指令定義檔，找出 `add`、`lw`、`call` 對應的樣式。
- 說：tinyc 的 `binary()` 函式與機器描述檔中的指令樣式在做同一件事。

## 什麼時候算融會貫通

- 看到一段 C 程式，能在紙上寫出任一熟悉 ISA 的 `-O0` 等價組合語言，並指出哪些地方最佳化器會改掉。
- 看到一份處理器手冊，能在一小時內列出「C 抽象機器的要求」與「這顆處理器的供給」的對照表，並預測工具鏈會在哪裡付出代價。
- 看到一個工具鏈錯誤訊息（連結失敗、對齊錯誤、未定義符號 `__divsi3`），能說出它屬於契約堆疊的哪一層。
- 能解釋為什麼 `-O2` 會讓一段依賴未定義行為的程式「壞掉」，並指出壞掉的那一層是程式而不是編譯器。
- 能說明自舉、交叉編譯與 Trusting Trust 之間的關係，以及它對今天供應鏈安全的意義。

## 範圍以外

本主題不處理：C++ 的物件模型與例外、JIT 與直譯器、作業系統載入器與動態連結的細節、特定廠商 SDK 的使用方式。這些都建立在同一疊契約上，可以在完成第 5 關後擴充。
