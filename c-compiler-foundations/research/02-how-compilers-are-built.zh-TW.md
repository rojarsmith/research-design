# 02 編譯器是怎麼被創造出來的

研究日期：2026-10-19。本文回答兩個常被混在一起的問題：編譯器內部如何運作，以及「第一個編譯器是誰編譯的」這個雞生蛋問題。配套的 [tinyc 實作](../labs/tinyc/README.md) 用不到一千行 Python 把每個階段寫成可讀的函式，建議對照閱讀。

## 編譯器是什麼

編譯器是一個把「一種語言的程式」翻成「另一種語言的程式」並保持語意的程式。對 C 來說，輸入是遵守 C 標準抽象機器語意的原始碼，輸出是特定處理器指令集加上特定 ABI 約定的組合語言或機器碼。中間的每一步都是在縮小「人的表達方式」與「機器能直接執行的東西」之間的距離。

## 經典管線

| 階段 | 輸入 → 輸出 | 做的事 | tinyc 對應 |
| --- | --- | --- | --- |
| 前置處理 | 文字 → 文字 | `#include`、巨集、條件編譯 | 未實作（C 前置處理是獨立的小語言） |
| 詞法分析 | 字元 → token | 把 `int x=10;` 切成 `int` `x` `=` `10` `;`，丟掉空白與註解 | `lex()` |
| 語法分析 | token → 抽象語法樹（AST） | 依文法規則組成樹狀結構，例如 `return` 節點下面掛一個 `+` 節點 | `Parser` 類別，每條文法規則一個方法 |
| 語意分析 | AST → 標注型別與符號的 AST | 查符號表、檢查型別、決定每個變數住哪裡 | `CodeGen` 內的 `lookup`、`declare_local`、型別回傳值 |
| 中間表示（IR） | AST → 與機器無關的低階表示 | GCC 的 GIMPLE／RTL、LLVM IR；讓最佳化與後端共用 | 未實作：tinyc 直接從 AST 生碼 |
| 最佳化 | IR → 更好的 IR | 常數折疊、消除死碼、迴圈不變量外提、暫存器配置前的重寫 | 未實作：對照 `clang -O2` 的輸出可看出差異 |
| 指令選擇與暫存器配置 | IR → 目標指令 | 把 IR 運算對應到指令樣式；決定哪些值住暫存器、哪些溢出到堆疊 | `Machine` 介面與 `RV32`、`X86_64` 兩個實作；策略最簡單：所有值經過累加器，暫存值放堆疊 |
| 組譯 | 組合語言 → 目的檔 | 符號解析、產生機器碼位元 | `rv32sim.py` 的前半段解析標籤；真正編碼可用 `clang -c` 看 |
| 連結 | 多個目的檔 → 可執行檔 | 合併區段、重定位、解析外部符號、套用 linker script | `runtime_rv32.s` 以串接檔案的方式扮演最小連結 |
| 載入與啟動 | 可執行檔 → 執行中的行程 | 載入器放好區段、`crt0` 設定堆疊與 `.bss`、呼叫 `main`，把回傳值交給 `exit` | `_start` 三行：`call main; li a7, 93; ecall` |

要點：**C 程式執行的第一條指令從來不是 `main` 的第一行。** 誰呼叫 `main`、誰把參數放進對的暫存器、誰在 `main` 回傳後結束程序，這些都是工具鏈（啟動碼與函式庫）的工作，而不是語言或處理器的。評估一顆處理器「能不能跑 C」時，這一層常被忽略。

## 前端與後端分離

Steve Johnson 的 PCC（1970 年代末）第一次把「理解 C」與「產生某種機器的指令」分成兩半。今天的架構是：

```
C ─┐                     ┌─ x86-64
C++┼─ 前端 ─ 共用 IR ─ 最佳化 ─ 後端 ┼─ AArch64
Rust┘                    └─ RISC-V / AVR / MSP430 ...
```

- GCC：前端產生 GENERIC → GIMPLE（最佳化主體）→ RTL（與機器描述檔 `.md` 配對做指令選擇）。
- LLVM：前端（Clang、rustc、swiftc）產生 LLVM IR；後端由 TableGen 描述的目標定義驅動。

這個結構的直接後果是：**為新處理器「寫一個 C 編譯器」在今天通常是指「為 GCC 或 LLVM 寫一個後端」**，而不是從詞法分析開始。後端要提供：暫存器檔案描述、指令樣式與選擇規則、呼叫慣例（ABI）、堆疊框架佈局、重定位型別，以及組譯器與連結器支援（binutils 或 LLVM MC）。

### 最小尺度的前後端分離：tinyc 的兩個後端

tinyc 把「後端必須知道的事」收斂成一個約三十個方法的 `Machine` 介面，再分別為 RV32IM 與 x86-64 實作。前端、型別規則、框架配置、控制流程、堆疊對齊的簿記全部共用；兩個後端各約 120 行。實際差異整理如下，這張表就是「移植編譯器到新處理器」在最小尺度上的全部內容：

| 項目 | RV32（ILP32 psABI） | x86-64（System V LP64） |
| --- | --- | --- |
| 指標大小 | 4 位元組，與 `int` 相同 | 8 位元組；`int *p` 需要較大的槽位，框架配置改問 `slot_size()` |
| 參數暫存器 | `a0` 至 `a7`，8 個 | `rdi rsi rdx rcx r8 r9`，6 個 |
| 回傳位址 | 放在 `ra`，由序曲存檔 | 由 `call` 指令自動壓入堆疊 |
| 比較結果變成 0／1 | `slt`、`seqz`、`snez`、`xori` | `cmpq` 後 `setcc` 再 `movzbq` |
| 除法 | `div`、`rem`，除以零有定義 | `cltd; idivl`，除以零會 trap |
| 全域變數位址 | `la`（絕對位址） | `leaq sym(%rip)`（位置無關） |
| 誰呼叫 `main` | tinyc 自己產生 `_start` | 借用主機 libc 的 crt0 |
| 內建輸出 | `ecall` | 呼叫 `runtime.c` 的一般函式 |

`run_tests.py` 的第四條路徑把 tinyc 的 x86-64 輸出交給主機的組譯器與 libc 連結後原生執行，五個範例的輸出與結束碼都與 gcc 相同。tinyc 產生的程式碼此時與真正的 `printf` 共用同一個堆疊，所以 ABI 規定的 16 位元組對齊不再是理論：對齊錯誤會讓 libc 內部使用對齊載入的指令當掉。

## 雞生蛋：第一個編譯器是誰編譯的

### 自舉（bootstrapping）

1. 先用已經存在的工具（組合語言、或另一台機器上的另一個語言）寫一個能處理語言子集的編譯器 C0。
2. 用這個子集寫出功能更完整的編譯器 C1 的原始碼，用 C0 編譯它。
3. 之後 C1 可以編譯自己（self-hosting）。再加功能時，只要新的原始碼仍是舊編譯器能處理的語言，就能繼續往上疊。

C 的歷史正是這樣：B 的編譯器最初用 BCPL 寫、之後用 B 自己重寫；C 的編譯器由 B 編譯器演化而來，很快就改以 C 撰寫並自我編譯。GCC 至今的建置流程仍保留三階段自舉（stage1 用系統編譯器、stage2 用 stage1、stage3 用 stage2，再比對 stage2 與 stage3 產出是否逐位元相同）作為正確性檢查。

### 交叉編譯（cross compilation）

處理器剛誕生時上面沒有任何軟體，所以第一個能為它產生程式的編譯器一定在別的機器上執行。慣用名詞：

| 名詞 | 執行於 | 產出給 | 例子 |
| --- | --- | --- | --- |
| 原生編譯器 | 機器 A | 機器 A | 桌機上的 `gcc` |
| 交叉編譯器 | 機器 A | 機器 B | 桌機上的 `riscv64-unknown-elf-gcc`、`arm-none-eabi-gcc` |
| Canadian cross | 在 A 上建置、在 B 上執行、產出給 C | 在 Linux 上建置給 Windows 用的 ARM 編譯器 |

絕大多數 MCU 永遠不會有原生編譯器，它們一輩子靠交叉編譯。所以「處理器能不能跑 C」與「處理器能不能跑 C 編譯器」是兩個不同的問題，前者容易得多。

### 信任問題

Ken Thompson 1984 年的圖靈獎演講〈Reflections on Trusting Trust〉指出：既然編譯器是用編譯器編譯出來的，一個在舊編譯器裡植入的後門可以在新編譯器裡自我複製，而且在原始碼中看不見。這也是為什麼可重現建置（reproducible builds）與 Diverse Double-Compiling 會被認真看待。對學習者的意義是：自舉不只是歷史趣聞，它是今天工具鏈供應鏈安全的核心問題。

## 幾個代表性的 C 編譯器

| 編譯器 | 時間 | 特點 | 適合用來學什麼 |
| --- | --- | --- | --- |
| Ritchie 的 PDP-11 C 編譯器 | 1972 至 1973 | 單一目標、直接生碼，極度精簡 | 歷史脈絡；原始碼可在 Unix 歷史典藏中找到 |
| PCC | 1977 年起 | 第一個可攜的 C 編譯器，前後端分離 | 可攜性的工程方法 |
| GCC | 1987 年 1.0 發布，Richard Stallman 起頭 | 自由軟體、支援數十種架構、三階段自舉 | 真實工業級後端的結構（`gcc/config/<arch>/`） |
| LLVM／Clang | LLVM 2000 年於 UIUC 開始（Chris Lattner、Vikram Adve），1.0 於 2003 年；Clang 2007 年由 Apple 啟動 | 以 IR 為中心的模組化設計、可當函式庫使用 | 現代編譯器架構；`clang -emit-llvm -S` 可直接看 IR |
| TCC（Tiny C Compiler） | Fabrice Bellard，2000 年代初 | 單一遍、極快，能即時編譯並執行 C | 單遍編譯器可以多簡單 |
| SDCC | 2000 年起 | 針對 8051、Z80、PIC、STM8 等 8 位元架構 | 沒有好堆疊、沒有大暫存器檔的處理器如何跑 C |
| chibicc | Rui Ueyama，2020 年 | 每個 commit 加一個功能，寫到能編譯自己 | 從零寫 C 編譯器的最佳閱讀材料；tinyc 的設計受它影響 |
| cproc、lcc、8cc、9cc | 各時期 | 小而完整 | 不同的 IR 與生碼策略 |

## 「為某處理器寫編譯器」到底需要什麼

把這個問題拆開，就能在 [03](03-processor-c-readiness.zh-TW.md) 中反過來評估處理器：

1. **目標描述**：暫存器數量與用途、指令與其運算元限制、定址模式、立即數範圍、分支距離。
2. **ABI**：參數怎麼傳、回傳值放哪、哪些暫存器被呼叫者保存、堆疊對齊、結構如何傳遞、`long`/指標多大（資料模型）。RISC-V 把這些寫在 psABI 文件中；tinyc 遵守其中的子集（`a0` 至 `a7` 傳參、`ra` 回傳位址、`sp` 16 位元組對齊）。
3. **執行期支援**：處理器沒有的運算要用函式庫補，例如沒有乘除法指令時的 `__mulsi3`、`__divsi3`，沒有浮點硬體時的軟體浮點。GCC 的 `libgcc` 與 LLVM 的 `compiler-rt` 就是這一層。
4. **啟動碼與連結腳本**：`crt0` 設定堆疊指標、清 `.bss`、複製 `.data` 從 Flash 到 RAM，然後呼叫 `main`；linker script 說明記憶體區域與區段擺放。
5. **C 函式庫**：hosted 環境要有完整 libc（glibc、musl）；freestanding／嵌入式常用 newlib、picolibc，只需要提供極少的系統呼叫樁（`_write`、`_sbrk` 等）。
6. **除錯與測試**：DWARF 除錯資訊、模擬器或 QEMU 目標、GCC torture 測試與 Csmith 之類的隨機測試。

## tinyc 與真實編譯器的差距

tinyc 刻意省略的東西，正是學習者下一步可以補的：

- 沒有前置處理器、沒有 `char`／`long`／`struct`／浮點、沒有字串常值。
- 沒有 IR 與最佳化：每個運算都經過堆疊，`fib(10)` 等五個範例平均比 `clang -O2` 多執行 3 至 50 倍指令（數字見 `run_tests.py` 輸出）。
- 暫存器配置是「全部都溢出」：每次讀變數都從記憶體載入。
- 沒有暫存器配置之外的任何最佳化；後端介面以「一個累加器加一個暫存器」為假設，無法表達真實後端的指令樣式與成本模型。

即便如此，tinyc 的 RV32 輸出能被 `clang --target=riscv32` 的整合組譯器組成真正的 RV32 機器碼，x86-64 輸出能在主機上與 libc 連結後原生執行，這證明「語言 → 指令集」這條路的本質並不複雜，複雜的是把它做到快、做到完整、做到正確。
