# 06 實測：同一組 C 程式編到 19 種處理器目標

研究日期：2026-10-19。本文是 [03 處理器評估](03-processor-c-readiness.zh-TW.md) 流程的實際執行結果。工具是 `labs/probe/compare_targets.py`，它用本機 clang 18.1.3 內建的後端，把 tinyc 的五個範例加上五個功能探針（乘除、64 位元整數、浮點、函式指標與 `switch`、`volatile` 與原子操作）編譯到 19 個目標，記錄三樣東西：前置處理器揭露的實作定義契約、`-O2` 下的 `.text` 大小與指令數，以及目的檔中未定義的 `__` 開頭符號，也就是「硬體沒有、要靠編譯器執行期函式庫補」的運算。完整原始輸出在 [labs/probe/results/](../labs/probe/results/)。

沒有任何一個目標在本環境真正執行；這是「用工具鏈回答處理器問題」的示範，執行層的驗證要靠模擬器或板子。

## 讀表前的四個提醒

1. 大小是 `llvm-size` 回報的 `.text`，含對齊填補；比較同一欄內的相對值即可，不要跨程式比。
2. `-O2` 偏重速度，`-Os` 會讓數字更接近嵌入式實務；腳本可改旗標重跑。
3. 執行期函式名稱依工具鏈而異：GCC 的 libgcc 與 LLVM 的 compiler-rt 用 `__mulsi3`，Arm 用 `__aeabi_*`，TI MSP430 用 `__mspabi_*`。名字不同，意思相同。
4. `nvptx64` 不能產生目的檔，只有指令數；`wasm32` 與 `bpf` 的 `.text` 是各自的區段格式。

## 第一層：實作定義的契約

| 目標 | `CHAR_BIT` | short／int／long／long long | 指標 | float／double | 位元組序 |
| --- | --- | --- | --- | --- | --- |
| avr（ATmega328P） | 8 | 2／2／4／8 | 2 | 4／4 | little |
| msp430 | 8 | 2／2／4／8 | 2 | 4／8 | little |
| cortex-m0、m4、m4f | 8 | 2／4／4／8 | 4 | 4／8 | little |
| rv32e、rv32i、rv32im、rv32imf | 8 | 2／4／4／8 | 4 | 4／8 | little |
| rv64gc、aarch64、x86-64 | 8 | 2／4／8／8 | 8 | 4／8 | little |
| i386、wasm32 | 8 | 2／4／4／8 | 4 | 4／8 | little |
| mips32、m68k、sparc | 8 | 2／4／4／8 | 4 | 4／8 | big |
| nvptx64、bpf | 8 | 2／4／8／8 | 8 | 4／8 | little |

觀察：

- **AVR 的 `int` 是 16 位元，`double` 是 4 位元組。** 任何假設 `int` 能放 100000 或 `double` 比 `float` 精確的程式在 AVR 上是錯的，而且編譯器不會警告。這就是 C 標準只規定下限的後果。GCC 10 以後的 avr-gcc 提供 `-mdouble=64`，clang 18 預設仍是 4。
- **MSP430 同樣是 16 位元 `int`，但 `double` 是 8 位元組**。兩顆同為 16 位元 MCU，契約卻不同；只看「幾位元」不夠。
- **三個 64 位元 Unix 目標都是 LP64**（`long` 8 位元組），32 位元目標是 ILP32。`long` 的大小在不同目標間變動是跨平台 bug 的經典來源，`stdint.h` 存在的理由就在這裡。
- **mips32、m68k、sparc 是大端序。** 這三個目標會讓所有「直接把結構寫進網路封包」的程式碼露出問題。
- **所有目標的 `CHAR_BIT` 都是 8。** clang 內建後端沒有字定址 DSP；`CHAR_BIT == 16` 的世界（TI C2000、部分 SHARC）只存在於廠商編譯器中。

觀察：

- **指令編碼寬度決定密度。** 同一個 `fib`，Thumb（Cortex-M0，16 位元編碼為主）248 位元組，rv32im（固定 4 位元組）484 位元組，rv64gc（含 C 壓縮擴充）410 位元組。指令數相近時大小差一倍，差的是編碼而不是演算法。MCU 選型看 Flash 容量時，這個差異直接影響成本。
- **rv32i 與 rv32im 在 02_loops 差 144 位元組**，差額全是乘除法變成函式呼叫的呼叫序列與參數搬移；函式庫本身的大小還沒算進來。
- **AVR 的 8 位元運算讓 03_pointers 膨脹到 229 條指令**，因為每個 16 位元 `int` 與指標運算都要拆成兩條 8 位元指令；MSP430 原生 16 位元，同一程式只要 117 條。
- **64 位元運算在 16 位元核心上是災難。** MSP430 的 11_long_long 要 492 位元組，是它自己 `fib` 的 1.8 倍；aarch64 只要 32 位元組。評估 MCU 時，程式裡有沒有 `long long`（或 `uint64_t` 時戳）值得單獨檢查。
- **mips32 普遍最大。** 固定 4 位元組編碼、延遲槽、沒有條件執行，再加上 `-O2` 展開；它是「ISA 設計年代」在數字上的體現。

## 第三層：執行期函式呼叫，也就是硬體缺口

未定義的 `__` 符號就是處理器沒有、必須由 libgcc 或 compiler-rt 以軟體補上的運算。

| 目標 | 乘除（10） | 64 位元（11） | 浮點（12） | 原子（14） | 啟動碼 |
| --- | --- | --- | --- | --- | --- |
| avr | `__divmodhi4`、`__udivmodhi4`（有乘法指令，無除法） | `__muldi3`、`__divdi3` | 全部軟體 | `__atomic_*_2` | `__do_clear_bss`、`__do_copy_data` |
| msp430 | `__mspabi_mpyi`、`__mspabi_divi` 等（連乘法都是呼叫） | `__mspabi_mpyll`、`__mspabi_divlli` | 全部軟體 | `__atomic_*_2` | |
| cortex-m0 | `__aeabi_idiv`、`__aeabi_uidiv`（有乘法，無除法） | `__aeabi_lmul`、`__aeabi_ldivmod`、`__aeabi_llsl` | 全部軟體 | `__atomic_*_4` | |
| cortex-m4 | 無（硬體除法） | `__aeabi_ldivmod` | 全部軟體 | `__atomic_*_4` | |
| cortex-m4f | 無 | `__aeabi_ldivmod` | 只剩 `__aeabi_ddiv`、`__aeabi_i2d`（單精度 FPU 不做 double） | `__atomic_*_4` | |
| rv32e、rv32i | `__mulsi3`、`__divsi3`、`__modsi3`、`__udivsi3` | `__muldi3`、`__divdi3` | 全部軟體 | `__atomic_*_4` | |
| rv32im | 無 | `__divdi3` | 全部軟體 | `__atomic_*_4` | |
| rv32imf | 無 | `__divdi3` | 只剩 `__divdf3`、`__floatsidf` | `__atomic_*_4` | |
| rv64gc | 無 | 無 | 無 | 無（A 擴充） | |
| i386 | 無 | `__divdi3` | 無（x87） | 無 | |
| x86-64、aarch64 | 無 | 無 | 無 | 無 | |
| mips32 | 無 | `__divdi3` | 無（假設有 FPU） | 無（ll／sc） | |
| m68k | 全部呼叫（預設 CPU 為 68000，無 32 位元乘除） | 全部呼叫 | 全部軟體 | `__atomic_*_4` | |
| sparc | 無 | `__divdi3`、`__ashldi3` | 無 | `__atomic_*_4`（v8 無 CAS） | |
| wasm32 | 無 | 無 | 無 | 無 | |

觀察：

- **「有乘法」與「有除法」是兩件事。** AVR 與 Cortex-M0 有乘法指令但沒有除法；MSP430 連乘法都沒有（硬體乘法器是周邊，不是指令）。評估時要分開問。
- **加了 FPU 不代表浮點全部免費。** Cortex-M4F 與 rv32imf 只有單精度，`double` 運算仍是軟體。程式中一個不小心寫成 `1.0` 而不是 `1.0f` 的常數，就會把整段運算拉回軟體浮點。
- **原子操作在單核心 MCU 上全是函式呼叫。** 編譯器不知道你的系統有沒有第二個核心，所以把 `__atomic_fetch_add_4` 交給 libc 或 RTOS 實作，通常是關中斷。這一層不存在時，連結會失敗。
- **AVR 的 `__do_clear_bss` 與 `__do_copy_data` 不是運算，是啟動碼。** 全域變數需要有人在 `main` 之前清零、把初始值從 Flash 搬到 RAM；這正是 [02](02-how-compilers-are-built.zh-TW.md) 所說「程式的第一條指令不是 `main`」在目的檔中留下的證據。
- **預設 CPU 型號會改變結論。** m68k 後端預設 68000，所以乘除全是呼叫；加 `-mcpu=68020` 會消失。評估時務必指定確切型號，不要用架構家族名稱。

## 兩個「不行」與一個「設計來當 C 目標」

- **bpf：不可以。** 有號除法、浮點、原子操作的回傳值都直接編譯錯誤。這不是後端沒寫完，而是 Linux eBPF 驗證器刻意限制的執行模型。它能跑 C 的子集，但「能否執行任意 C 程式」的答案是否定的。
- **nvptx64：子集。** 十個程式有九個能編，但 `memory_order_acquire` 的原子載入在後端選不到指令。GPU 的記憶體模型與 C11 的對應不完整，加上沒有目的檔與連結器的一般流程，它是 C 方言（CUDA C）的目標，不是 C 的目標。
- **wasm32：全部通過，且沒有任何執行期呼叫。** WebAssembly 不是處理器，但它被設計成 C／C++ 的編譯目標，64 位元整數與浮點都是原生指令。這說明「能跑 C」的關鍵在於指令集是否覆蓋 C 抽象機器，而不在於它是矽還是虛擬機。

## 對應到 03 的結論格式

| 目標 | 結論 | 主要代價或限制 |
| --- | --- | --- |
| x86-64、aarch64、rv64gc | 可以 | 無 |
| i386、mips32、sparc、cortex-m4f、rv32imf | 可以 | 64 位元除法或 double 走軟體；sparc 原子操作走軟體 |
| cortex-m4、rv32im | 可以但有代價 | 浮點全部軟體；原子操作需系統提供 |
| cortex-m0、rv32i、rv32e、m68k（68000） | 可以但有代價 | 乘除法軟體化，迴圈密集程式慢 10 倍以上；需限制使用浮點與 64 位元 |
| msp430 | 可以但有代價 | 16 位元 `int`、乘法也是呼叫、64 位元運算昂貴；需要編碼規範 |
| avr | 可以但有代價 | 16 位元 `int`、4 位元組 `double`、2 位元組指標、哈佛架構常數需 `__flash`；需要編碼規範與程式碼審查 |
| wasm32 | 可以 | 不是處理器；執行環境另計 |
| nvptx64 | 子集 | 記憶體模型與主機流程不同；只在 CUDA C 的框架內使用 |
| bpf | 不可以（作為一般 C 目標） | 設計上禁止的運算會直接編譯失敗 |

## 重現與擴充

```sh
cd c-compiler-foundations/labs/probe
python3 compare_targets.py --json results/my-run.json > results/my-run.md
python3 compare_targets.py --targets avr,rv32i,cortex-m0      # 只跑幾個
```

要加入自己的候選處理器，在 `TARGETS` 加一列（名稱、clang triple、額外旗標、說明）；要加入自己的程式，放進 `features/`。有交叉工具鏈時，下一步是把 [probe.c](../labs/probe/probe.c) 在模擬器或板子上執行，補上這裡缺少的執行層證據。
