# C 語言、編譯器與處理器：從起源到可驗證的理解

研究日期：2026-10-19。本主題回答三個問題，並示範如何把它們當成同一件事來理解：

1. C 語言是怎麼被創造出來的？
2. 編譯器是怎麼被創造出來的，第一個編譯器又是誰編譯的？
3. 如何評估一款處理器能否執行 C 編譯後的軟體？

第四篇把三者放進一疊「契約」裡，並給出六關可驗證的學習路線。配套的實作練習包含一個約一千行的 C 子集編譯器（共用前端，RV32 與 x86-64 兩個後端）、一個 RV32IM 模擬器與一組差分測試；所有範例在本環境中以三種編譯器、兩種處理器、四種組合執行，輸出完全一致。

## 核心結論

- **C 是對一台抽象機器的描述語言。** Ritchie 把 1972 年 PDP-11 的能力（位元組定址、堆疊、間接存取、整數運算）抽象成語言，後來的 ISO 標準把這台機器寫成條文。C 的指標、陣列退化、未定義行為，都可以從「要能便宜地翻成當年的機器指令」解釋。
- **編譯器是把抽象機器翻到某個指令集並遵守一份 ABI 的程式。** 詞法、語法、語意、IR、最佳化、生碼、組譯、連結、啟動碼各司其職；第一個編譯器靠自舉與交叉編譯取得。今天「為新處理器寫 C 編譯器」通常指為 GCC 或 LLVM 寫後端。tinyc 的兩個後端各約 120 行，其餘全部共用，差異表見 02。
- **處理器能否跑 C，是工具鏈問題多於硬體問題。** 硬體決定代價（暫存器數量、定址模式、乘除、堆疊、位址空間是否統一），工具鏈決定可不可以（後端、ABI、執行期函式庫、libc、啟動碼、除錯）。評估結論分成「可以／可以但有代價／不可以」，並以探針程式與代價量測為證據。
- **融會貫通的方式是把語言、編譯器、ABI、ISA、微架構看成一疊各自承諾不同事情的契約。** 同一個 `fib` 程式穿過每一層時長什麼樣子，在實作練習中可以逐層印出來。

## 五分鐘開始

```sh
cd c-compiler-foundations/labs/tinyc
python3 run_tests.py
```

本環境的輸出摘要（Ubuntu 24.04，gcc 13.3，clang 18.1）：

| 範例 | tinyc → rv32sim 執行指令數 | clang -O2 → rv32sim 執行指令數 | tinyc x86-64 原生 | 主機 gcc 原生 | 四者輸出 |
| --- | --- | --- | --- | --- | --- |
| 01_fib | 18863 | 5327 | 通過 | 通過 | 一致 |
| 02_loops | 4523 | 580 | 通過 | 通過 | 一致 |
| 03_pointers | 5321 | 183 | 通過 | 通過 | 一致 |
| 04_globals（結束碼 7） | 1061 | 88 | 通過 | 通過 | 一致 |
| 05_logic | 7051 | 134 | 通過 | 通過 | 一致 |

tinyc 的 RV32 輸出也能用 `clang --target=riscv32 -march=rv32im -c` 組成真正的 RV32 ELF 目的檔；x86-64 輸出以主機 `cc` 組譯、與 `runtime.c` 連結後在主機 CPU 上原生執行。指令數差距來自 tinyc 沒有暫存器配置與最佳化，這本身就是 02 與 04 的教材。

## 建議閱讀順序

1. 先跑 `run_tests.py`，看到四條路徑一致。
2. 讀 [04](research/04-integration-path.zh-TW.md) 的契約堆疊圖，建立整體框架。
3. 依序讀 01、02、03。每篇都會指回實作練習中的具體程式碼或指令。
4. 從 [04](research/04-integration-path.zh-TW.md) 的第 1 關開始動手。

## 範圍與限制

- 歷史敘述以 Ritchie 與 Thompson 的第一手回顧及標準組織頁面為準，年份精確到年。
- 本環境沒有 RISC-V GCC、QEMU 或實體板，因此「真實硬體」部分以 clang 的 riscv32 後端與整合組譯器驗證到機器碼為止，執行驗證在自製模擬器上完成。
- tinyc 是教學用的 C 子集，刻意省略前置處理器、`char`、結構、浮點與最佳化；缺少的功能列在 [tinyc 技術說明](labs/tinyc/README.md) 中作為練習。x86-64 後端只為了對照前後端差異而存在，不處理 `long long` 以外 LP64 帶來的其他型別問題。
- 處理器類別的工具鏈限制會隨版本改變，實際評估時以當時版本的手冊為準。
